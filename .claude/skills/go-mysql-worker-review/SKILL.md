# Go + MySQL 常時稼働ワーカー レビュー

外部サービスの状態を受け取って MySQL に保存し続ける処理を、設計と実装の両面でレビューする。

判断の根拠と実測値は、このリポジトリの `調査`（設計ガイド）と `docs/measurements.md`（実測結果）にある。
指摘するときは **§番号を添える**。「なぜそうなのか」がその節に書いてある。

## 進め方

1. **対象を掴む** — どこが受信（WebSocket / Kafka / SSE）で、どこが取得（API ポーリング）で、
   どこが書き込みかを最初に特定する。この3つが混ざっている設計は、たいてい §2.1 で崩れている。
2. **下の「機械的に見つかるもの」を先に潰す** — grep で当たる。ここで大半が出る。
3. **残りを設計の観点で読む** — 特に「A（全件同期）が無い」「不明とオフラインが同じ値」
   「1テナント1担当が保証されていない」の3つは、grep では出ないが影響が最も大きい。
4. **指摘は「壊れ方」で書く** — 「§4.2 違反」ではなく
   「比較用 struct に observed_at が入っているので、常に変化ありと判定され、毎秒 DB に書きに行く」と書く。

## 機械的に見つかるもの

| 探すもの | 何が問題か |
| --- | --- |
| `grep -rn "map\[string\]any\|map\[string\]interface{}" --include=*.go` の JSON 解析部 | メモリ 15〜26倍・割り当て 22〜30倍（§6.1） |
| `grep -rn "DisallowUnknownFields"` | API に項目が1つ増えただけで全件同期が止まる（§6.3） |
| `grep -rn "SetMaxOpenConns"` と `SetMaxIdleConns` の対応 | `MaxIdleConns` の既定値は **2**。設定漏れで毎回張り直しになる（§5.2・実測: 300クエリで接続 205本 vs 10本） |
| `grep -rn "SetConnMaxIdleTime"` が無い | `wait_timeout` で切られた接続を掴んだままになる（§5.2） |
| `sql.Open` の呼び出し箇所 | **プロセスに1つ**か。テナントごと・リクエストごとに開いていないか（§5.1） |
| `time.Time` を含む struct を `==` や `!=` で比較 | 毎回「変化あり」になり、書かない工夫が丸ごと無効になる（§4.2 の罠） |
| `float64` / `float32` をそのまま比較 | 同上。丸めてから比較する（§4.2） |
| `ON DUPLICATE KEY UPDATE` に `observed_at` の比較が無い | 遅れて届いた古い情報が新しい状態を上書きする（§2.7） |
| `INSERT ... VALUES(col)`（旧構文） | MySQL 8.0.20 以降は `AS new` + `new.col`。旧構文は非推奨警告が出る（実測で確認済み） |
| バッチ送信の直前に `sort` が無い | すれ違う順序で行を触るとデッドロック（§4.3・実測で再現可能） |
| `SELECT ... FOR UPDATE` でテナント処理を直列化 | テナント数ぶん詰まる。冪等性で守る（§2.7） |
| `Begin()` と `Commit()` の間に HTTP 呼び出し | トランザクションを開いたまま外部 API を待つ（§4.6） |
| WebSocket 実装に `Ping` / `SetReadDeadline` が無い | 接続は生きたまま無音になっても永久に気づかない（§2.6） |
| 現在状態のテーブルが `INSERT` だけ | 行が無限に増え、読むたびに最新1件を探すことになる（§4.4） |
| 履歴テーブルに保持期間の仕組みが無い | `DELETE` は undo 肥大・purge 遅延で高くつく。RANGE パーティション＋`DROP PARTITION`（実測 15倍速い） |

## 設計として確認すること

**状態同期（§2）**
- WebSocket を状態の正解として使っていないか。**イベントは差分、状態は取りに行く**
- 起動時に API から全件取得しているか。準備完了の宣言はその**後**か（§2.3）
- **定期的な全件同期（A）があるか**。鮮度チェック（B）だけでは、
  ① 名簿に増えた対象 ② 間違っているが新しい値 を永久に拾えない（§2.2）
- 名簿を API から取っているか。元気なものだけが流れてくるストリームから名簿は作れない
- 「不明」がオフラインと別の値になっているか。沈黙からオフラインと判定していないか（§2.4/§2.5）
- API が答えないとき「不明」のままにしているか（嘘をつかない）

**冪等性と競合（§2.7 / §2.8）**
- 書き込みが `observed_at` の比較で冪等か（A・B・C の到着順が入れ替わっても壊れないか）
- **1テナント1担当がリース等で保証されているか**。無いと二重稼働するが、**普段は動いてしまう**
- 送信元の時刻が秒単位しかない場合、同じ秒の中の変化が捨てられていないか（連番が要る）

**メモリ（§3）**
- メモリに置いているものが全部「消えても作り直せるもの」か。
  **欠測が許されない履歴をバッファに載せていないか**
- `committed` の更新が DB 書き込み**成功後**か。失敗時に据え置いて再送しているか
- 名簿から消えたキーを掃除しているか

**DB 負荷（§4）** — 効く順に ①書かない ②まとめて書く ③表を分ける ④読み取りを DB に来させない
- 変化がないときに書いていないか（実測: 1,000件/秒・変化率1% で **1000 → 10.7 tx/s**）
- 鮮度を毎回書いていないか（近況報告は30〜60秒ごと・対象ごとにずらす）
- バッファがキー付き（map）か。配列だと重複排除が効かない
- バッチを1トランザクションにまとめているか（実測: 100行で **114ms → 4.4ms**）

**観測（§7）** — これが無いと調整できない
- 毎分 `received` / `changed` / `touched` / `skipped` を出しているか
- **変化率（changed / received）が見えるか**。全設計判断の前提になる
- 監視が「接続の有無」ではなく「最後に受信した時刻」を見ているか

## 動くコードで確かめる

指摘が「本当にそうなるか」を相手に見せたいときは、このリポジトリの実装とテストを使う。

| 見せたいこと | 使うもの |
| --- | --- |
| 比較用 struct に時刻を入れると壊れる | `internal/worker/tracker_test.go` の `TestStateに時刻やポインタを入れていない`（reflect で機械的に検出。**他プロジェクトにそのまま移植できる**） |
| 変化がなければ書かない効果 | `cmd/loadsim`（3方式のトランザクション数を比較） |
| バッチの効果 | `go test ./internal/store/ -bench Write` |
| ソートしないとデッドロックする | `internal/store/store_test.go` の `TestBatch_ソートしないとデッドロックする` |
| 二重稼働の防止 | `internal/lease/`（リース。8コンテナが同時に取りに行っても担当は1つ） |
| 沈黙をオフラインと判定しない | `internal/app/app_test.go` の `TestUnknown_APIが答えないときは不明のままにする` |
| 接続は生きているのに無音 | `TestSilent_接続は生きているのに何も来ない` / `TestPing_応答が無ければ自分から切って繋ぎ直す` |
| MySQL の挙動（affected_rows・パーティション・undo・プール） | `go test ./internal/mysqlfacts/ -v` |

## 数字を出すときの約束

- **実測値は測定条件とセットで出す**（`docs/measurements.md` に条件を書いてある）
- **環境が違えば絶対値は変わる。桁の関係だけが変わらない**
- 未確認のことは「未確認」と言う。推定を実測のように書かない
