# Go + MySQL リポジトリ層 レビュー

根拠と実測は `docs/repository-layer.md`、実装例は `internal/repo/` にある。
指摘するときは **「どう壊れるか」を具体的に**書く（「§違反」ではなく「他テナントの行が消える」）。

## 進め方

1. **テナント分離の担保がどこにあるか**を最初に確認する。
   「全員が毎回 `tenant_id` を書く」なら、それは担保されていない（いつか忘れる）
2. 下の grep を当てる。ほとんどの事故はここで出る
3. 残りを「更新の消失」「実行計画」「トランザクションの中身」の観点で読む

## 機械的に見つかるもの

| 探すもの | 何が問題か |
| --- | --- |
| `UPDATE`/`DELETE` の SQL で `tenant_id` を含まないもの | 他テナントの行を書き換える。実験では tenant_id 忘れの UPDATE が他テナントの行を書き換えた |
| `db.Exec` / `db.Query` の戻り値の `RowsAffected` を捨てている | WHERE を間違えても気づけない。実験では1行のつもりが5行に当たった |
| `SELECT ... ` → Go で加工 → `UPDATE ...`（read-modify-write） | 更新が消える。実験では 200回中 175回が消えた。`version` か DB 側計算に |
| `OFFSET` を使ったページ送り | 深いほど遅い（4,000件目で 2.19ms vs 0.36ms）。キーセット法へ |
| ループの中の `QueryRow` / `Get` | N+1。500件で 40〜64倍。`IN` か範囲でまとめる |
| `LIMIT` の無い `SELECT` | 行数が増えた日に落ちる。件数上限を決める |
| `SELECT *` | 要らない列まで運ぶ（実測 1.4倍）。一覧では特に効く |
| `PRIMARY KEY (id)` ＋ `KEY (tenant_id)` のマルチテナント表 | テナント単位の読み出しが 2.6倍遅い。`PRIMARY KEY (tenant_id, id)` に |
| `CHAR(36)`/`BINARY(16)` のランダム UUID を主キーにしている | 表サイズ 2.0倍・投入 1.5倍。主キーは連番か UUIDv7、UUID は UNIQUE 索引で |
| `UNIQUE KEY` に `tenant_id` が入っていない | 他テナントの登録を弾く（`UNIQUE (serial)` は事故のもと） |
| `SELECT ... FOR UPDATE` の多用 | 詰まる・デッドロックの主因。冪等な書き方か楽観ロックへ |
| `Begin()` 〜 `Commit()` の間の HTTP 呼び出し | 長いトランザクション（undo が伸びる）。やり直しが二重送信になる |
| デッドロック（1213）を握りつぶす / リトライが無い | すれ違う順序の更新は必ず起きる。やり直せる形にする |
| `*sql.DB` をリポジトリやサービスに配って回っている | どこからでも何でも書ける。テナント束縛したハンドルを配る |
| driver のエラー番号（1062 など）が業務コードに出てくる | `ErrConflict` などの型に寄せる |

## 設計として確認すること

- **テナントの値をアプリが書かないで済む形になっているか**
  （`internal/repo` では SQL に `:tenant` と書き、値は層が差し込む。無ければ実行しない）
- **更新が「何行に当たるか」を宣言しているか**（`ExpectOne` 相当）。宣言と違えばロールバックしているか
- **読んで書く箇所に version があるか**。あるいは、そもそも読まずに済ませられないか
- **ページ送り・一括取得に上限があるか**。上限を超えたらエラーにしているか
- **実行計画をテストで固定しているか**。そのテストのデータ量は本番に近いか
  （実験: 50行だと別の索引 + filesort、5,000行だと PRIMARY の range。少ない件数で固定しても意味がない）
- **問い合わせ回数をテストで縛っているか**（N+1 はスロークエリログに出ない）
- **逃げ道（テナント横断・全件取得・生の `*sql.DB`）が、塞がれるのではなく記録されているか**
- **接続プールがプロセス単位か**、`SetMaxIdleConns` を設定しているか（既定値は 2）

## 動くコードで確かめる

| 見せたいこと | 使うもの |
| --- | --- |
| tenant_id 忘れ・WHERE ミス・更新消失が実際に起きること | `go test ./internal/repo/ -run TestExperiment_ -v` |
| 層がそれを止めること | `go test ./internal/repo/ -run 'TestScope\|TestRepo\|TestTx' -v` |
| 実行計画・問い合わせ回数をテストで縛る書き方 | `internal/repo/repotest/`（他プロジェクトへそのまま持って行ける） |
| 検査の代金（往復の 0.06%） | `go test ./internal/repo/ -bench 'PointRead\|CheckAndBind' -benchmem` |

## 数字を出すときの約束

- 実測値は測定条件とセットで（`docs/repository-layer.md` に条件を書いてある）
- 環境が違えば絶対値は変わる。**桁と比だけが変わらない**
- 実行計画の話をするときは、**必ず件数を添える**（件数で計画は変わる）
