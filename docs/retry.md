# 一時 vs 恒久エラーの分類とリトライ（EXP-49）

何でもリトライしてはいけない。**恒久エラー**（重複キー・構文・制約違反）は何度叩いても失敗する
＝すぐ諦める(fail-fast)べきで、リトライは DB と外部を無駄に叩くだけ。**一時エラー**（デッドロック
1213・ロック待ちタイムアウト 1205・接続断）だけをバックオフして再試行する。分類器 `Retryable` で
「retry してよいか」を判定してから retry するのが要点。

実装は [internal/retrylab](../internal/retrylab)、receipt は
[docs/results/exp-49](results/exp-49/exp-49-retry-classification.md)。

## 結果（実 MySQL のエラーで測定）

| ケース | 分類 | Do の試行回数 | 結果 |
| --- | --- | --- | --- |
| 恒久：重複キー(1062) | Retryable=**false** | **1**（fail-fast） | 即失敗 |
| （素朴に「何でも 5 回 retry」した場合） | — | 5（無駄叩き） | 失敗 |
| 一時：ロック待ちタイムアウト(1205) | Retryable=**true** | **2** | retry して成功 |

- **恒久エラー**（id 再 INSERT → 1062）は 1 回で確定。何でも retry する素朴版は同じ恒久エラーを
  **5 回**叩いてから諦める（DB を無駄に叩き、エラーを隠す）。
- **一時エラー**：別トランザクションが X ロックを保持中に UPDATE すると、victim 接続
  （`innodb_lock_wait_timeout=1`）は attempt1 で 1 秒待って **1205**（retryable）→ backoff →
  ロックが解けた頃の **attempt2 で成功**（計 2 回・約 1.3s）。
- 分類器は `1213/1205 → true`、`1062 → false`、`nil → false` を返す。

## 要点

- **分類してから retry**。`Retryable(err)` を先に判定し、恒久は即失敗・一時だけ backoff 再試行。
  「何でも retry」は恒久エラーを隠して DB を無駄に叩き、原因究明も遅らせる。
- **一時エラー**は MySQL エラー番号で見分ける：`1213`（デッドロック）・`1205`（ロック待ち
  タイムアウト）。加えて接続断 `driver.ErrBadConn` は張り直して retry（[EXP-33](db-resilience.md)）。
- **デッドロック(1213)は tx 丸ごと retry**。片方が犠牲になり自動ロールバックされるので、
  部分再実行はできない（トランザクション全体をやり直す）。
- **backoff は指数＋ジッタ**が実務的（同時に落ちたクライアントが一斉に再試行して雪崩になるのを防ぐ）。
  **回数上限**と**全体タイムアウト**の両方で頭打ちにする（[EXP-45 dead-letter](dead-letter.md) と接続）。
- 一意制約違反(1062)は基本恒久だが、「後勝ちにしたい」設計なら retry でなく **upsert** にする
  （設計で恒久エラー自体を消す）。境界は文脈次第。

## 保証しない範囲・未検証

- backoff は本実験では固定間隔（300ms）。実務は指数＋ジッタを推奨（本実験は分類の正しさが主眼）。
- エラー分類の境界（どれを一時とみなすか）はアプリの文脈次第。ここは 1213/1205/接続断を一時とした。
- デッドロックの実発生（EXP は 1205 で一時エラーを代表）や、外部 API の 5xx/タイムアウト分類は本実験外。
- 全体タイムアウト・サーキットブレーカとの組み合わせは運用設計（本実験外）。
