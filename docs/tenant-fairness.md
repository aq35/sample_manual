# ノイジーネイバー対策（テナント公平性）（EXP-34）

マルチテナントでは、1テナント(hog)がキューに大量投入すると、素朴な「到着順に捌く」では
他テナント(victim)の命令が hog の後ろで延々待たされる。テナントをまたいで公平に回せば、
victim は hog の量に関係なくすぐ捌ける。

実装は [internal/fairnesslab](../internal/fairnesslab)、receipt は
[docs/results/exp-34](results/exp-34/exp-34-tenant-fairness.md)。

## 結果（hog 2000件が先着・victim 5テナント各1件が後着）

| 捌き方 | victim の最悪待ち位置 |
| --- | --- |
| 到着順（unfair） | **2004**（hog を全部捌いた後） |
| テナント round-robin（fair） | **5**（テナント数ぶん） |

「待ち位置」= その命令が捌かれる前に処理された件数。待ち時間 ≒ 位置 × 1件の処理時間。
総処理量は同じで、変わるのは**順序**。到着順だと 1テナントの流量が他全員の遅延になる。

## 指針

- **ワーカーはテナントをまたいで公平に回す**（round-robin / 重み付き）。「pending を古い順に
  全体から」ではなく、「各テナントから少しずつ」。
- **1テナントが1周で取れる量に上限**（per-tenant batch cap）。hog がいても1周の取り分は一定。
- **担当をワーカーで分ける**（[lease](fencing.md)・[fan-out fold](fanout.md)）と、テナントが別
  ワーカーに散り、hog の影響がそのワーカー内に閉じる。
- **流入側でも守る**: テナント単位のレート制限（[EXP-26](graphql.md)）で、そもそも1テナントが
  大量投入しすぎないようにする。
- 完全な飢餓防止には「pending が古くなりすぎた命令を優先」等の劣化対策も足す（公平とレイテンシ
  SLA の両立）。

## 適用範囲・保証しない範囲

- ここは「捌く順序」の比較。実際の待ち時間は 1件の処理時間に比例する（位置はその係数）。
- round-robin は単純な公平化。プラン別の重み付けや hog 上限は要件で選ぶ。
- 複数ワーカー・lease による分散の効果は EXP-2/14 側。ここは単一キューの順序に集中。
