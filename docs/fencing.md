# EXP-2 lease / fencing / 時計のずれ — 古い担当の書き込みを止める

再現:

```bash
eval "$(./scripts/mysql-up.sh --export)"
go test ./internal/fencelab/ -run TestEXP2 -v -timeout 20m
```

結果ファイル: [`docs/results/exp-2/exp-2-lease-fencing-clock-skew.md`](results/exp-2/exp-2-lease-fencing-clock-skew.md)

---

## 1. 守りたい不変条件

```
1. lease を失った worker は、それ以降 commit できない
2. 新しい担当の fence より古い write は拒否される
3. プロセスの自己申告時刻だけで lease を奪えない
4. 同時に claim したとき、勝者は1つ
```

## 2. 結果

### 2.1 停止していた worker が再開したとき（GC の長い停止・OS による停止）

worker A を**書き込み直前で止め**、その間に lease を期限切れにして B が担当を取り、
そのあと A を再開させた。

| 方式 | 古い担当の書き込みで受理されたもの |
| --- | --- |
| DB 時計の lease（fence なし） | **1 件（事故）** |
| DB 時計の lease ＋ fence | **0 件** |

**lease だけでは止まらない。** A は「まだ自分が担当」と思っており、
延長の確認をしていても、確認から書き込みまでの間に担当が変わりうる。

止まるのは、**書き込み条件そのものに世代番号（fence）を入れたとき**だけ。

```sql
UPDATE fence_state SET v = ?, fence = ?, writer = ?
 WHERE tenant_id = ? AND k = 'counter'
   AND fence <= ?     -- ★古い担当はここで落ちる
```

判断しているのは worker ではなく **DB**。worker が何を信じていても関係ない。

### 2.2 時計のずれ

A が正常に担当を保持している間に、**時計が60秒進んだ** B が担当を取りに来た。

| 期限の判定に使う時計 | 奪われたか |
| --- | --- |
| 各プロセスの時計 | **奪われた（事故）** |
| DB の時計（`NOW(3)`） | 奪われない |

**期限の判定に使う時計は1つに決める。** 各プロセスが自分の時計で
「切れている」と判断してよいことにすると、時計がずれたプロセスが乗っ取れる。

### 2.3 同時 claim

8プロセスを同時に起動して claim させた。

| 方式 | 勝者 |
| --- | --- |
| 担当を決めない | **8（全員が書ける＝二重稼働）** |
| lease（DB 時計） | 1 |
| lease ＋ fence | 1 |

## 3. 測定器を疑った2件（実験そのものの誤り）

**結果より先に、測り方を2回直した。**

### 3.1 「勝者」を時間で数えていた

最初の測定では lease 方式でも勝者が 3 と出た。実装ではなく**数え方**が誤りで、
勝った worker が仕事を終えて担当を手放したあと、次の worker が正当に取り直したものまで
「勝者」として数えていた。

→ 勝者は**同じ瞬間**で数える必要がある。各 worker に担当を持ったまま待たせて測り直した。

### 3.2 `affected_rows` で所有権を判定していた

lease の延長を

```sql
UPDATE fence_lease SET expires_at = ? WHERE tenant_id = ? AND owner = ?
```

の影響行数で判定していたところ、**取得と延長が同じミリ秒に起きると `expires_at` が
同じ値になり、MySQL が「0 行」と報告する**ため、担当を持っているのに
「担当を失った」と誤判定してプロセスが止まった（5ms で終了していた）。

→ `clientFoundRows=true` を DSN に付け、影響行数を「一致した行」にした。
これは以前 `docs/measurements.md` §9 で確認した「値が変わらない UPDATE は 0 行」の帰結で、
**所有権の判定に `affected_rows` を使うときは必ず踏む**。

## 4. 適用範囲と未検証

**当てはまる範囲**

- MySQL 8.0 / 単一インスタンス / 同一ホストの複数プロセス
- 停止は SIGUSR1 待ちで再現（その間プロセスは何もしない、という点で GC の長い停止と同じ）
- fence は DB の1行で単調増加させている（外部の採番サービスは使っていない）

**保証しないこと**

- ネットワーク分断（DB へは届くが worker 同士は見えない）は未再現
- **DB のフェイルオーバーで fence 行が巻き戻る場合は未検証。**
  fence の単調性が壊れると、この仕組み全体が成り立たない
- NTP による時刻の飛び（時計が後ろ向きに跳ぶ）は未再現
- 接続占有型ロック（`GET_LOCK`）は担当の表現としては測っていない。
  接続を占有し続けること・期限が無いことの問題は `docs/locking.md` 3.7

## 5. 実装するときの型

```go
// 1. 担当を取る（期限の判定は DB の時計）
ok, err := worker.Acquire(ctx)      // fence 番号を受け取る

// 2. 書くときは必ず fence を添える
accepted, err := worker.Write(ctx, value)   // WHERE fence <= ?

// 3. accepted == false は「担当を失っていた」。retry してはいけない
```

- fence を**書き込み条件**に入れる。ログに出すだけでは意味がない
- 受理・拒否の両方を監査表に残す。「誰の書き込みが通ったか」は事後に必ず聞かれる
- `accepted == false` を「一時的な失敗」として再試行しない。**担当が変わっている**
