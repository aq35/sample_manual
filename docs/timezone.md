# 時刻の保存と DST スケジューリング（EXP-35）

always-on スケジューラの定番バグは「タイムゾーンと夏時間(DST)」。実測で2つ確かめた。

実装は [internal/tzlab](../internal/tzlab)、receipt は
[docs/results/exp-35](results/exp-35/exp-35-timezone-dst.md)。

## 1. 現地時刻の繰返し予定は DST で壊れる

`America/New_York` の 2026 年で:

| 切替 | 現地時刻 | 何が起きるか |
| --- | --- | --- |
| 春（3/8, 02:00→03:00） | 02:30 は**存在しない** | `time.Date(..02:30..NY)` は 02:30 を保てず別の時刻に正規化（Go は 01:30 になった。方向は実装依存） |
| 秋（11/1, 02:00→01:00） | 01:30 が**二重**に起きる | 現地表示 01:30 が UTC で1時間違う 2 つの瞬間になる |

- 「毎日 02:30（現地）」を素朴に `time.Date` で作ると、**春は予定が消える/ずれる、秋は二重発火**しうる。
- 対策: 現地の繰返し予定は tz 対応で計算し、**存在しない時刻・二重の時刻を明示的に解決**する
  （例: 存在しなければ切替後の最初の有効時刻へ、二重なら最初の一方だけ、と決める）。可能なら
  スケジュールも UTC で持ち、現地表示は表示時だけ変換する。

## 2. DATETIME と TIMESTAMP はセッション tz で挙動が違う

`+00:00` で `2026-06-01 12:00:00` を入れ、`+09:00` で読むと:

| 型 | 読めた値（+09:00） | 意味 |
| --- | --- | --- |
| `DATETIME` | `2026-06-01 12:00:00`（不変） | tz 無視の literal。入れたまま |
| `TIMESTAMP` | `2026-06-01 21:00:00`（+9h） | UTC 保存で、セッション tz へ変換 |

- **混在させない**。方針を1つに:
  - **推奨: 瞬間は UTC で持つ**。`TIMESTAMP` を使い、アプリ・DB のセッション tz を UTC 固定で
    一貫させる（このリポジトリは DSN `loc=UTC`）。または epoch 整数。
  - `DATETIME` を使うなら「値は常に UTC の壁時計」という**規約**を全経路で守る（tz 変換に頼らない）。
- go-sql-driver の `loc` / `parseTime` とセッション tz が食い違うと、読み書きで無言でずれる。
  設定を1つに固定して、テストで往復（入れて読む）を確かめる。

## 指針（まとめ）

- **保存は UTC**（予定 `scheduled_for`・実績 `observed_at` とも）。計算も基本 UTC。
- **現地の繰返し予定だけ** tz 対応ライブラリで計算し、gap（春）・二重（秋）を明示的に解決。
- DATETIME/TIMESTAMP は**方針を1つに**して混在させない。DSN のセッション tz を固定し、往復テスト。
- ログ・API の表示は「保存 UTC → 表示時に現地変換」。保存を現地時刻にしない。

## 保証しない範囲・未検証

- 対象地域の tz は運用による（ここは US で代表）。閏秒は扱わない。
- MySQL の named time zone（`'America/New_York'`）は tz テーブル投入が要る。数値オフセットは常に可。
- Go の gap 時刻の正規化方向は実装依存（「02:30 を保てない」ことが要点で、どちらへ寄るかは頼らない）。
