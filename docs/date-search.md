# 日付範囲検索は何件で重くなるか（EXP-18）

- 実験: `internal/datelab` / 結果: `docs/results/exp-18/exp-18-date-range-search.md`

## 結論

**重さは「テーブルの総行数」ではなく「範囲がヒットして走査/返す行数」で決まる。**
`(tenant_id, observed_date)` の索引があれば、日付範囲はテナント局所の range scan になり、
所要はヒット行数にほぼ比例する。

## 総行数は効かない・ヒット行数が効く

同じ「1日」の検索（行は365日に均等散布）:

| 総行数 | ヒット行数 | p50 | EXPLAIN |
| --- | --- | --- | --- |
| 100,000 | 274 | 0.66ms | type=range rows=274 |
| 1,000,000 | 2,740 | 2.0ms | type=range rows=2740 |

総行数が10倍でも、range scan が触るのは**ヒット行数だけ**（EXPLAIN rows = matched）。
遅くなったのは総行数のせいではなく、密度が上がって1日のヒットが 274→2,740 に増えたから。

## 範囲幅（＝ヒット行数）で所要が決まる（1M行・covering COUNT）

| 範囲 | ヒット行数 | p50 | 計画 |
| --- | --- | --- | --- |
| 1日 | 2,740 | 2.1ms | range / Using index |
| 7日 | 19,178 | 10.4ms | range / Using index |
| 30日 | 82,192 | 43ms | range / Using index |
| 180日 | 493,151 | **620ms** | **ref**（半分の行。索引の利きが変わる） |

ほぼ線形。**目安（このホスト・索引だけで完結する場合）**: 数千行 ≈ 数 ms、〜1万行 ≈ 10ms、
〜10万行 ≈ 数十 ms、〜50万行 ≈ 数百 ms。

## いちばん効くのは covering かどうか（本体行へのランダムアクセス）

30日（82,192行ヒット）で、索引だけで済む場合と、`payload`（索引に無い列）を取る場合:

| | p50 |
| --- | --- |
| covering（COUNT / 索引列だけ） | 43ms |
| payload も取る（本体行へ 82,192 回引きに行く） | **472ms（約11倍）** |

**同じヒット行数でも、索引外の列を取ると桁が変わる。** だから「何件で重くなるか」は、
返す列が索引に載っているか（covering か）で大きく動く。

## 範囲が広すぎると full scan

全期間（365日≒全100万行）では `type=ref key=PRIMARY rows≈54万` と、実質全走査になる。
範囲がテーブルの大部分を占めると、オプティマイザは索引をやめて全走査に切り替える（EXP-7 と同じ）。

## 日付検索を重くしないための設計

1. **索引は `(tenant_id, observed_date, ...)`**。テナント先頭で、日付範囲をテナント局所に。
   日付だけの索引は他テナントまで走査する。
2. **必要な列を索引に載せて covering にする**（`(tenant_id, observed_date, id, status)` など）。
   本体行へのランダムアクセスが 11 倍効く。
3. **範囲を絞る / keyset でページング**（OFFSET 深堀りは避ける。EXP-7）。
   画面は「1日」「1週間」など狭い既定に。
4. **巨大な追記表は日付でパーティション**（EXP-15）。pruning が効き、古いのは `DROP PARTITION`。
5. **返す行数が多い検索は集計に寄せる**（COUNT / GROUP BY は covering で速い。生行を数十万返さない）。

**まとめ**: 索引が正しければ「総行数◯件で重くなる」ではなく「1クエリが**返す行数**◯件で重くなる」。
covering なら数万行まで数十 ms、payload を引くなら数千行で重くなり始める。数十万行を返す検索は、
範囲を絞るか集計にする。
