# 排他制御 — GET_LOCK は要るのか、代わりに何があるか

「複数のコンテナが同時に動いていて、この処理は1つだけ走ってほしい」に対する答えを、
実験して決めたもの。再現:

```bash
eval "$(./scripts/mysql-up.sh --export)"
go test ./internal/repo/ -run TestExperimentLock_ -v   # 根拠になった実験
go test ./internal/repo/ -run TestWithLock -v          # 正しい使い方の確認
```

測定環境は `docs/measurements.md` と同じ（MySQL 8.0.46 / Go 1.24.7 / 同一ホスト）。

---

## 1. 結論（何を使うか）

| やりたいこと | 使うもの | 理由 |
| --- | --- | --- |
| **マイグレーションを1つだけ走らせる** | **`GET_LOCK`（接続を固定して）** | DDL は暗黙コミットするので、行ロック方式は最初の DDL で外れる。ユーザーロックだけが DDL をまたいで保持される |
| 日次集計など、数秒〜数分で終わる処理を1つだけ | `GET_LOCK`（同上） | 接続を1本占有するが、短時間なら許容できる |
| **ワーカーの担当テナントを決める（長時間）** | **期限つきリース**（`internal/lease`） | `GET_LOCK` は接続を占有し続け、期限も無い。20テナントで接続20本を占有し、プールが枯渇した |
| 1行の更新が競合する | **楽観ロック（version）／ DB 側で計算** | ロックは要らない。`docs/repository-layer.md` 2.3 |
| 数行の整合性を保つ（DDL を含まない） | トランザクション＋行ロック（`FOR UPDATE`） | コミット／ロールバックで自動的に解放される。デッドロック検出も効く |
| 「同時に起動しても壊れなければよい」だけ | **ロックを使わない**（冪等にする・一意キーで先に記録する） | 下の 2 を参照 |

**先に言っておくと、いちばん効くのは「マイグレーションをアプリの起動時に走らせない」**
（別のジョブ／init コンテナで1回だけ流す）。それができるなら、以下の話の大半は要らなくなる。
ただし現実には起動時に流す構成が多いので、その場合の作り方を以下に書く。

---

## 2. そもそもロックは要るのか

**実験**（`TestExperimentLock_ロック無しで同時にDDLを流す`）。
8つのコンテナが同時に「未適用なら DDL を流して記録する」をロック無しでやると:

```
ロック無しで8並列: 7/8 が失敗
  7 件: DDL: Error 1050 (42S01): Table 'exp_nolock' already exists
適用の記録: 1 件
```

**DDL 自体は1つしか通らないので DB は壊れない。問題は残り7つが起動に失敗すること。**
Kubernetes なら、そのコンテナは再起動を繰り返す。

### 代替: ロックを使わず「先に記録する」（insert-first）

**実験**（`TestExperimentLock_先に記録する方式`）。
`INSERT INTO schema_migrations (version) VALUES (1)` を**先に**撃ち、
一意制約に勝った1つだけが DDL を流す:

```
① 先に記録する方式・8並列: 適用 1 / 見送り 7 / エラー 0
```

**ロック無しでも、エラーは出ない。** 並行性だけを見るならこれで足りる。

ただし **途中で落ちたとき** の壊れ方が違う。

| 方式 | 途中で落ちると | 次の起動 |
| --- | --- | --- |
| 先に記録する | 記録あり・DDL 未適用 | **「適用済み」と判断して飛ばす → 永久に当たらない** |
| ロック＋後で記録 | DDL 適用済み・記録なし | 同じ DDL を再実行して `Error 1050` で落ちる |

**どちらもクラッシュには弱い。ロックは「同時に走らせない」ためのもので、
「途中で落ちる」には効かない。** 両方を別に手当てする（→ 6）。

## 3. GET_LOCK の性質（実験でわかったこと）

### 3.1 ★接続（セッション）に紐づく — プールごしに使うと壊れる

**実験**（`TestExperimentLock_接続に紐づく`）。`*sql.DB` のメソッドで `GET_LOCK` を呼び、
別の呼び出しで `RELEASE_LOCK` すると:

```
① プールごしの RELEASE_LOCK: 0 ＝ 解放できていない（別の接続が持っている）
   → ロックはまだ接続 11 が持っている。プールに残った接続が持ち続ける
```

`database/sql` はどの接続に行くかを保証しない。**取得と解放が別の接続に行く。**
さらに悪いことに（`TestExperimentLock_プールに残ったロックは他の処理に見える`）:

```
ロックを持ったままプールに戻った接続を、別の処理が借りた:
  IS_FREE_LOCK=0, その処理が RELEASE_LOCK=1
```

**まったく無関係な処理が、他人のロックを解放できてしまう。**

> **対策は1つだけ: `db.Conn()` で接続を固定し、取得・解放・その間の処理を全部その接続で行う。**
> このリポジトリでは `repo.DB.WithLock` がそれを閉じ込めている。

### 3.2 ★DDL をまたいで保持される（行ロックは外れる）

**実験**（`TestExperimentLock_DDLは行ロックを外す`）。
「ロック用の行を `SELECT ... FOR UPDATE`」という代替案は、**マイグレーションでは使えない**。

```
★ A が DDL を1つ実行した時点で、A の行ロックは外れていた（DDL の暗黙コミット）
  → B が同時にマイグレーションを始められる
★ GET_LOCK は DDL をまたいでも保持される
```

MySQL の DDL は暗黙にコミットする。コミットすれば行ロックは解放される。
**これがマイグレーションで `GET_LOCK` を選ぶ決定的な理由。**

### 3.3 トランザクションと無関係

`ROLLBACK` してもユーザーロックは解放されない（`TestExperimentLock_トランザクションと無関係`）。
3.2 の裏返しで、良い面でもあり悪い面でもある。**明示的に解放するか、接続を閉じるまで残る。**

### 3.4 名前はサーバ全体で共通

**実験**（`TestExperimentLock_名前はサーバ全体で共通`）。別のデータベース（`workerdb2`）に
接続していても、同じ名前のロックは取れない。

> **対策: 名前にスキーマ名を含める。** `WithLock` は `workerdb.migrate` のように自動で付ける。
> なお名前は **64文字まで**（超えるとエラー）。`WithLock` は実行前に弾く。

### 3.5 待ち方と、持ち主の確認

**実験**（`TestExperimentLock_待ち方と状態の確認`）。

| | |
| --- | --- |
| `GET_LOCK(name, 0)` | 待たずに諦める（結果 0、所要 0s） |
| `GET_LOCK(name, 1)` | 1秒待って諦める（所要 1.001s） |
| `IS_USED_LOCK(name)` | 持っている接続 ID（誰も持っていなければ NULL） |
| `IS_FREE_LOCK(name)` | 空いていれば 1 |

**同じセッションが同じ名前を2回取ると、参照カウントが増える**（解放も2回必要）。
`defer` で1回ずつ対応させるのが安全。

### 3.6 接続が切れれば即座に解放される

**実験**（`TestExperimentLock_接続が切れたら解放される`）。`KILL` した瞬間に解放された。
**プロセスが落ちてもロックは残らない。** これは Redis の SETNX を手で書く場合より優れている点
（あちらは TTL を自分で管理し、期限切れと生存を両立させる必要がある）。

ただし **アプリが固まっていて接続だけ生きている場合は、持ち続ける。**
これが「長時間の担当」に使えない理由（3.7）。

### 3.7 長時間の「担当」には向かない

**実験**（`TestExperimentLock_長時間の担当には向かない`）。
20テナントの担当を `GET_LOCK` で表すと:

```
20 テナントの担当を GET_LOCK で保持 → 接続を 20 本、保持している間ずっと占有する
→ プールが枯渇し、通常の問い合わせが取れなくなった
```

DB の接続は有限（`調査` §5: コンテナ数 × テナント数 × 接続数）。
**担当を持つ = 接続を持つ、という設計は掛け算で破綻する。**
この用途は `internal/lease` の期限つきリース（行 + `expires_at` を延長し続ける）が正しい。

### 3.8 代金

**実験**（`TestExperimentLock_代金`）。

| | 1回あたり |
| --- | --- |
| `GET_LOCK` + `RELEASE_LOCK`（往復2回） | 348 µs |
| `BEGIN` + `FOR UPDATE` + `COMMIT`（往復3回） | 373 µs |

**ロックの種類による差ではなく、往復の回数の差。** どちらも `調査` §1 の「1往復 ≒ 0.1〜1ms」の話。

### 3.9 確かめていないこと

- **レプリケーションされない。** ユーザーロックはバイナリログに乗らないので、
  レプリカや、フェイルオーバー後の新しいプライマリには引き継がれない
  （この環境は単一インスタンスなので未検証。**採用前に自分の構成で確認すること**）
- **複数書き込みノード**（Galera / Aurora マルチマスター等）では、
  ノードをまたいだ排他にならない可能性が高い

## 4. 代替の比較

| 手段 | 解放のされ方 | DDL をまたげるか | 接続を占有するか | 期限 | 向く用途 |
| --- | --- | --- | --- | --- | --- |
| **`GET_LOCK`** | 明示 or 接続断で即時 | **○** | **する（1本）** | 無し | マイグレーション、短い排他処理 |
| 行ロック（`FOR UPDATE`） | コミット／ロールバック | ✗（暗黙コミットで外れる） | トランザクション中のみ | `innodb_lock_wait_timeout` | 数行の整合性 |
| **期限つきリース**（行 + `expires_at`） | 期限切れ | ○ | しない | **あり** | 長時間の担当・ワーカー割り当て |
| 一意キーで先に記録 | — | ○ | しない | — | 「1回だけ実行」。ただしクラッシュに弱い |
| 楽観ロック（`version`） | — | — | しない | — | 1行の更新競合 |
| 外部（Redis / k8s Lease） | TTL | ○ | しない | あり | DB を持たない処理、複数 DB をまたぐ排他 |

**MySQL しか無い環境で「排他したい」と思ったら、まずこの表のどれかに当てはめる。**
`GET_LOCK` は万能ではないが、**マイグレーションに関しては代わりが無い**（3.2）。

## 5. 正しい使い方（`repo.DB.WithLock`）

```go
err := db.WithLock(ctx, "daily_rollup", 10*time.Second, func(ctx context.Context) error {
    return doRollup(ctx)   // ここは同時に1つだけ走る
})
if errors.Is(err, repo.ErrLockNotAcquired) {
    // 他のコンテナが走っている。今回は見送る
    return nil
}
```

実装で外せない点は3つ。

1. **`db.Conn()` で接続を固定する**（3.1）。`*sql.DB` のまま呼ばない
2. **`defer` で必ず解放する**。解放も同じ接続で行う
3. **名前にスキーマ名を付ける**（3.4）。長さも確認する

`WithLock` はこれを閉じ込めてあり、次を回帰テストで守っている
（`TestWithLock_終わったら必ず解放される`）。

- 20回繰り返してもロックが残らない
- 中でエラーになっても解放される
- 終わったら接続がプールに戻る（`使用中 0`）

**やってはいけない使い方**

- 長時間（分〜時間）保持する → 接続を占有する。リースを使う
- ロックの中で外部 API を呼ぶ → 相手が固まるとロックも固まる
- ロックが取れなかったときに、黙って処理を続ける → 排他の意味が無い

## 6. マイグレーションの設計（この2つを別々に手当てする）

### 6.1 同時に走らせない → `GET_LOCK`

`repo.Migrate` は `WithLock(ctx, "migrate", 30秒)` の中で全部を行う。
8並列で呼んでも適用は1回だけ（`TestMigrate_同時に起動しても壊れない`）。

待ち時間（`Options.MigrateLockWait`、既定30秒）は、
**いちばん長いマイグレーションより長く**しておく。短いと、後続のコンテナが
「待ちきれずに起動失敗」になる。

### 6.2 途中で落ちたときに気づく → 二相の記録

記録を `started` → `done` の二相にしてある。

```
① INSERT ... state='started'   ← 始めることを記録
② DDL を流す
③ UPDATE ... state='done'      ← 終わったことを記録
```

次の起動で `started` のまま残っていれば、**起動を止めて人に知らせる**
（`ErrMigrationUnfinished`、`TestMigrate_途中で終わっていたら止まる`）。
黙って飛ばすと「永久に当たらないマイグレーション」になり、黙って再実行すると
`Error 1050` で毎回落ちる（2 の表）。

### 6.3 記録用の表を後から変えるときの技

`schema_migrations` に `state` 列を足したとき、**既定値を `'done'` にした**。
こうすると `ALTER TABLE ... ADD COLUMN` の時点で既存行が全部 `done` になり、
**埋めるための `UPDATE` が要らない**。

行数が多い表では、この「既定値で埋める」が効く。埋める `UPDATE` は重いうえ、
途中で落ちると中途半端になる。

> ちなみに最初は `UPDATE ... WHERE finished_at IS NULL` で埋めようとして、
> **自分で入れた `sql_safe_updates=1` に弾かれた**（キー列を使わない UPDATE）。
> 安全網は自分にも効く。

### 6.4 DDL は冪等に書けるなら書く

`CREATE TABLE IF NOT EXISTS` は使えるが、`CREATE INDEX` には `IF NOT EXISTS` が無い
（MySQL 8.0）。冪等にできない DDL は、6.2 の「止めて人に知らせる」で受ける。

## 7. チェックリスト

- [ ] `GET_LOCK` を `*sql.DB` のメソッドで直接呼んでいないか（**接続を固定しているか**）
- [ ] 解放が `defer` にあり、取得と同じ接続で行われるか
- [ ] ロック名にスキーマ名／アプリ名が入っているか（サーバ全体で共有される）
- [ ] ロックが取れなかったときの動きが決まっているか（待つ／見送る／落ちる）
- [ ] 長時間の担当に使っていないか（→ 期限つきリース）
- [ ] ロックの中で外部 API を呼んでいないか
- [ ] **「同時に走らない」と「途中で落ちる」を別々に手当てしているか**
- [ ] マイグレーションの待ち時間が、いちばん長いマイグレーションより長いか
- [ ] レプリカ構成／フェイルオーバー時の挙動を確認したか（ユーザーロックは引き継がれない）
