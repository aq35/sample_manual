# SQLite へ持ち込めるもの・持ち込めないもの（EXP-10）

- 実験: `internal/sqlitefacts` / `go test ./internal/sqlitefacts/ -run TestEXP10 -v`
- 結果: [docs/results/exp-10/exp-10-sqlite-companion.md](results/exp-10/exp-10-sqlite-companion.md)（JSON も同じ場所）
- 実行 SHA は結果ファイルの先頭にある

## この文書がやらないこと

**MySQL の結論を SQLite の結論として流用しない。**
「MySQL でこうだったから SQLite でもこうだろう」と書いた行は1つも無い。
12 個の問いを**同じ実行の中で両方のエンジンへ投げ**、
観測値が一致したかどうかだけで分類している（`internal/sqlitefacts/probe.go`）。

分類は4つ。

| 分類 | 意味 |
| --- | --- |
| `SAME_SEMANTICS` | 同じコードで同じ観測値。そのまま持ち込める |
| `DIFFERENT_MECHANISM` | 同じ結果にできるが、**書き方を変える**必要がある |
| `DIFFERENT_RESULT` | 同じコードで**違う結果**。持ち込むと壊れる |
| `UNVERIFIED` | 片方（または両方）を測れていない |

片方が測れなかった問いは `SAME` にしない。
実際、最初の実行では MySQL 側の `CREATE TRIGGER` が権限で失敗しており、
それを「MySQL では守れない」と読める観測値として返していた。
**測れなかったことを結論にしない**ように、失敗はエラーとして返して `UNVERIFIED` へ落とすよう直した
（設定を変えて測れるなら測り直す。いまは `log_bin_trust_function_creators` を
一時的に立てて測り、元へ戻している）。

## 結果

### そのまま持ち込めないもの（`DIFFERENT_RESULT`）

| 問い | MySQL | SQLite |
| --- | --- | --- |
| 同じ値へ UPDATE したときの影響行数 | 0 行 | 1 行 |
| UPSERT の影響行数（挿入 / 更新 / 変化なし） | 1 / 2 / 0 | 1 / 1 / 1 |
| 整数列へ `'abc'` を入れる | 拒否される（Error 1366） | **入る**（読み戻すと `"abc"`） |
| `UPDATE ... RETURNING` | 使えない（構文エラー） | 使える |
| 時刻の混在（Go の `time.Time` と SQL リテラル） | 同時刻の行が 2 件見つかる（正しい） | **1 件しか見つからない** |

いちばん危ないのは最後の2つ。

**① 影響行数。** repo 層の `Expect`（EXP-2 の fencing、楽観ロック）は
「UPDATE が何行に当たったか」で持ち主を判定している。
MySQL は既定で「実際に値が変わった行数」を返すので、同じ値への更新は 0 になる
（EXP-2 で踏んで `clientFoundRows=true` で回避した罠）。
SQLite は「処理した行数」を返すので 1 になる。
**同じ `Expect` のコードが、エンジンによって逆の判定をする。**

**② 時刻。** SQLite に日時型は無い。
`WHERE expires_at < ?` の比較は、格納されている**文字列の辞書順**になる。
実験では、Go の `time.Time` を束縛して入れた行が `"2026-01-02 03:04:05 +0000 UTC"`、
SQL リテラルで入れた行が `"2026-01-02 03:04:05"` になり、
**同じ時刻なのに `=` で一致しなかった**（MySQL は 2 件、SQLite は 1 件）。
lease の期限判定（EXP-2）はこの形そのものなので、
移植するなら「入れ方を1つに固定する」ことが必須になる。

### 書き方を変えれば同じにできるもの（`DIFFERENT_MECHANISM`）

| 問い | MySQL | SQLite |
| --- | --- | --- |
| トランザクション内の DDL を ROLLBACK | 残る（暗黙にコミットされる） | **消える**（DDL もトランザクションに入る） |
| 外部キーの既定 | 検査される | **検査されない**（`foreign_keys` は既定 OFF、しかも接続ごと） |
| WHERE の無い UPDATE | `sql_safe_updates` で止まる | 止まらない（相当物が無い） |
| 名前つきロック | `GET_LOCK` がある | 無い（`BEGIN IMMEDIATE` で作る） |

**DDL のトランザクション性は、SQLite のほうが楽になる数少ない点。**
EXP-6（マイグレーション crash matrix）で必要だった「どこまで進んだかの記録」は、
4本のマイグレーションを1トランザクションで流して3本目で失敗させたところ、
**残った表は 0 個**だった。跡形もなく戻るので、段階の記録は要らなくなる。
ただし、その間じゅう書き込みロックを握るので、
「起動時に他のプロセスが書けない」点は MySQL と同じ問題として残る。

### 同じだったもの（`SAME_SEMANTICS`）

- 追記専用の表をトリガで守れる（MySQL は `SIGNAL`、SQLite は `RAISE(ABORT)`。書き方は違うが結果は同じ）
- 時刻の列を `DATETIME` と宣言し、**入れ方を1つに揃えれば**往復で同じ値になる

## SQLite だけで起きる事故

### ① PRAGMA は接続ごと

```go
db, _ := sql.Open("sqlite", "file:app.db")
db.Exec("PRAGMA foreign_keys = ON")   // ★これが事故
```

プールの 4 本の接続に対して、**効いていたのは 1 本だけ**（実測 1/4）。
外部キー検査が効いている接続と効いていない接続が混ざり、
どちらに当たるかは実行のたびに変わる。テストでは通って本番で壊れる形。

対策は DSN に書くこと。新しい接続すべてに当たる（実測 4/4）。

```go
sql.Open("sqlite", "file:app.db?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=journal_mode(WAL)")
```

### ② `BEGIN`（DEFERRED）の昇格

「読んでから書く」トランザクションを 2 本同時に走らせた（20 回 × 2 本 = 40）。

| 開始のしかた | 成功 | 進めなかった |
| --- | --- | --- |
| `BEGIN`（既定の DEFERRED） | 20 | **20** |
| `BEGIN IMMEDIATE` | 40 | 0 |

DEFERRED は読み取りロックから始まり、最初の書き込みで昇格しようとする。
両方が読んでから書くと、片方は昇格できない。
**このとき `busy_timeout` は助けにならない**（相手も同じ場所で待っているので順番が来ない）。
`BEGIN IMMEDIATE` は最初から書き込みロックを取るので、待てば必ず順番が来る。

`database/sql` の `BeginTx` は DEFERRED になる。
読んでから書くトランザクションは、接続を固定して `BEGIN IMMEDIATE` を自分で流す。

### ③ WAL を使わないと、読み手が止まる

書き手 1 本・読み手 3 本を同時に 1 秒動かした。

| journal_mode | 書き込み | 読み取り | 読み取り p99 |
| --- | --- | --- | --- |
| `delete`（既定） | 1,194 | **88** | **329 ms** |
| `wal` | 11,277 | 59,895 | 309 µs |

読み取りが 88 件しか通らず、p99 が 0.3 秒。約 680 倍の差。
**WAL は「速くする設定」ではなく「読み手と書き手を同時に動かすための設定」。**

### ④ 別プロセスからの書き込み

3 プロセスが同じファイルを 1 秒書いた（本物の別プロセス。OS のファイルロック越しに競合する）。

| 条件 | 成功 | SQLITE_BUSY |
| --- | --- | --- |
| `delete` / `busy_timeout=0` | 772 | **185,978** |
| `wal` / `busy_timeout=0` | 38,394 | 56,720 |
| `wal` / `busy_timeout=5s` | 48,762 | **0** |

`busy_timeout` を入れないと、成功 1 件あたり 240 件の `SQLITE_BUSY` が出る。
なお 3 プロセスの内訳は均等ではなかった（23,286 / 18,369 / 8,640）。
**SQLite の書き込みロックは公平ではない**ので、
「全プロセスが同じだけ進む」前提のワーカー設計は成り立たない。

### ⑤ `.db` だけをコピーしたバックアップ

300 行を書いた直後（チェックポイント前）にバックアップして、別の場所で開き直した。

| 方法 | 復元後の行数 | integrity_check | 中身のハッシュ |
| --- | --- | --- | --- |
| `.db` だけをコピー | **0**（元 300） | `ok` | 不一致 |
| `.db` + `-wal` + `-shm` | 300 | `ok` | 一致 |
| `VACUUM INTO` | 300 | `ok` | 一致 |

**`integrity_check` が `ok` を返しても、中身が同じとは限らない。**
壊れていない空のデータベースは、整合してはいる。
だから検査は「行数」でも「コマンドが成功したか」でもなく、
**中身のハッシュを突き合わせる**（`sqlitefacts.Verify`）。

WAL モードでは、コミット済みのデータは `-wal` 側に載っている。
`.db` だけを持っていくと、**成功したはずの書き込みが消える**。

## ドライバの選択

`modernc.org/sqlite`（C を Go へ変換したもの、cgo 不要）と
`github.com/mattn/go-sqlite3`（本家 C を cgo で呼ぶ）を、同じ条件で比べた。

| | pure Go | cgo |
| --- | --- | --- |
| 書き込み | 39,306 /s（p50 13.9 µs） | 49,684 /s（p50 9.7 µs） |
| 読み取り | 100,279 /s（p50 8.2 µs） | 130,895 /s（p50 6.0 µs） |
| 実行ファイル（linux-amd64） | 8.8 MiB | 6.5 MiB |
| SQLite のバージョン | 3.46.0 | 3.46.1 |

cgo 版のほうが 25〜30% 速い。配布は pure Go 版が圧倒的に楽。

| ビルド条件 | ビルド | 実行 |
| --- | --- | --- |
| pure Go / linux-amd64 | できる 8.8 MiB | できる |
| pure Go / linux-arm64（クロス） | できる 8.5 MiB | （このホストでは実行できない） |
| pure Go / darwin-arm64（クロス） | できる 8.6 MiB | （同上） |
| cgo / linux-amd64 `CGO_ENABLED=1` | できる 6.5 MiB | できる |
| cgo / linux-amd64 `CGO_ENABLED=0` | **できてしまう** 2.9 MiB | **失敗する** |
| cgo / linux-arm64 `CGO_ENABLED=1`（クロス） | できない（arm64 の C コンパイラが無い） | — |

★ここが罠。`CGO_ENABLED=0` で cgo 版をビルドすると、**ビルドは通る**。
落ちるのは実行時で、`Binary was compiled with 'CGO_ENABLED=0', go-sqlite3 requires cgo to work`。
**「クロスコンパイルできるか」を `go build` の終了コードで判断すると取り違える。**
だから `cmd/sizeprobe` は開くだけでなく、書いて読み戻すところまでやっている。

### 観測値はドライバによらないか

12 個の問いを両方のドライバへ投げた。**1つだけ食い違った。**

`TEXT` と宣言した列へ Go の `time.Time` を束縛して入れたときの格納形:

| ドライバ | 格納された文字列 |
| --- | --- |
| modernc（pure Go） | `2026-01-02 03:04:05 +0000 UTC` |
| mattn（cgo） | `2026-01-02 03:04:05+00:00` |

**同じファイルを、途中でドライバを変えて読み書きすると、時刻が2種類の書式で混ざる。**
辞書順で比較しているので、混ざった時点で並び順が壊れる。
時刻は必ず自分で書式を決めて文字列として入れる（`time.Time` をそのまま束縛しない）。

## 反証された仮説

**仮説2「`MaxOpenConns` を増やしても書き込みスループットは上がらず、`SQLITE_BUSY` が増える」は間違いだった。**

| 並行数 / MaxOpenConns | 成功 | BUSY | p99 |
| --- | --- | --- | --- |
| 1 / 1 | 43,150 | 0 | 51 µs |
| 4 / 1 | **25,312** | 0 | 500 µs |
| 4 / 4 | 47,855 | 0 | 864 µs |
| 8 / 8 | 43,243 | 0 | 1.33 ms |

- `BUSY` は 1 件も出なかった。`busy_timeout=5s` があるので、**エラーにならず待つ**（増えるのは遅延であってエラーではない）
- `MaxOpenConns=1` は、4 並行のとき**むしろ遅い**（25,312 対 47,855）。
  書き込みが直列であることと、`database/sql` の 1 本を奪い合うことは別の話だった

「書き込みは直列だから接続は1本でいい」という直感は、**測ったら逆だった**。
ただしこれは同一プロセス内の話で、別プロセス間では ④ のとおり `BUSY` が出る。

**仮説1「ドライバが違っても観測値は同じ」も、1件で反証された**（上の時刻の書式）。

## 測っていないこと

- **電源断・カーネルパニック。** `synchronous` が守るのはここだが、このホストでは作れない
- ネットワーク越しのファイル（NFS / EFS / SMB）でのロック。SQLite 本家が推奨していない構成
- 複数ホストからの同時書き込み（SQLite では成り立たない前提）
- レプリケーション（litestream / LiteFS など）
- 暗号化・全文検索など拡張が要る機能。pure Go 版と cgo 版で差が出る可能性がある
- **`ops/sec` の絶対値を MySQL と比べること。** 同じホストの同じ条件で測ったドライバ間の比較にしか使えない

### `synchronous` で失うものは測れていない（LIVE_ENV_REQUIRED）

```
| journal / synchronous | 書き込み /s | p50 |
| delete / FULL         |     1,236  | 776 µs |
| delete / OFF          |    31,201  |  27 µs |
| wal    / FULL         |     6,529  | 131 µs |
| wal    / NORMAL       |    44,787  |  13 µs |
| wal    / OFF          |    63,664  |  13 µs |
```

速度差は 50 倍あるが、**ここで測ったのは速度だけ**。

測れたのは「プロセスが死んでも残るか」まで。
200 件をコミットした直後（`EXP_KILL_AT=after_commit`）に自分を SIGKILL したところ、
`synchronous` が `FULL` / `NORMAL` / `OFF` のどれでも **200 件すべて残っていた**。
コミット済みのデータは OS のページキャッシュにあるので、プロセスが死んだくらいでは消えない。

**プロセス死と電源断は別の事故で、`synchronous` が効くのは後者。**
本当に測るには次が要る（このホストではできない）。

1. 専用のホスト（VM でよいが、ホスト側のキャッシュを切ること）
2. `journal_mode` × `synchronous` の組み合わせごとに、連番を1件1トランザクションで書き続ける
3. 書いている最中に**電源を切る**（VM なら `virsh destroy` / `kill -9 qemu`。`reboot` では意味が無い）
4. 起動し直して、**最後にコミットが返った連番**と、実際に残っている最大の連番を突き合わせる
5. `PRAGMA integrity_check` と、中身のハッシュ（`sqlitefacts.Verify`）
6. 収集する項目: 失われた件数 / 破損の有無 / 復旧に要した操作

## 移植するなら（このリポジトリの実装に対して）

| 部品 | どうなるか |
| --- | --- |
| `repo.Expect`（影響行数） | **書き換えが要る。** 同じ値への更新で MySQL は 0、SQLite は 1 |
| `repo.Scope`（テナント束縛） | そのまま。文字列検査（EXP-8）は方言に依存していない |
| `repo.WithLock`（`GET_LOCK`） | **作り直し。** `BEGIN IMMEDIATE` を取れた側だけが進む形にする |
| `repo.Migrate`（段階の記録） | **単純になる。** DDL がロールバックできるので、途中で落ちても跡が残らない |
| lease の期限判定（EXP-2） | **危ない。** 時刻の書式を1つに固定してからでないと動かない |
| `sql_safe_updates` に頼っていた部分 | 相当物が無い。文字列検査と `Expect` の比重が上がる |
| 接続プールの上限（EXP-5） | 意味が変わる。**プロセス内では 1 本より複数本のほうが速かった**（反証された仮説を参照） |
| EXPLAIN の回帰テスト（EXP-7） | `EXPLAIN QUERY PLAN` は出力の形が全く違う。作り直し |

## 測定器の側で見つかった間違い

**`journal_mode=delete` の実験が、実は全部 WAL で走っていた。**

子プロセスへ `exec.Command(bin, "-wal", "false")` と 2 引数で渡していた。
Go の `flag` はこれを「`-wal=true` と、位置引数 `"false"`」と解釈する。
その結果、「WAL 無し」の条件で `SQLITE_BUSY` が 1 件も出ず、
**「別プロセスからの書き込みは競合しない」という誤った結論**が出ていた。

直したあとの数字が上の ④。0 件 → 185,978 件。

対策として、子プロセスに `journal_mode` を報告させ、
**要求したモードで動いていなければテストを落とす**ようにした。
条件が設定できていないことに気づけない実験は、何も測っていないのと同じ。

（`bool` フラグは `-wal=false` の形で渡す。これは Go の `flag` の仕様。）
