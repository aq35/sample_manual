# 可観測性：何を測るか・ラベル設計・記録コスト（EXP-37）

本番で「気づける」ようにする最小限。要点は **RED を境界で取る／ラベルは有界なものだけ／記録
コストは気にしなくてよい**。時系列の爆発（カーディナリティ）だけが本当の落とし穴。

実装は [internal/metrics](../internal/metrics)（カーディナリティ上限つきカウンタと遅延
ヒストグラム）、receipt は [docs/results/exp-37](results/exp-37/exp-37-observability.md)。

## 何を測るか（RED）

境界（Web ハンドラ・Worker の1件処理）で:
- **Rate**: 処理数/秒（カウンタ）。
- **Errors**: 失敗数/秒（カウンタ。エラー種別は有界なラベルで）。
- **Duration**: レイテンシ分布（ヒストグラム。p50/p95/p99 を出す）。

キュー・プールは USE（Utilization/Saturation/Errors）も: プール使用率・待ち数・[EXP-5](pool-saturation.md) の膝。

## ラベル設計（唯一の落とし穴＝カーディナリティ）

時系列の数 = **ラベル値の直積**。実測（10万リクエスト）:

| ラベル | 時系列数 |
| --- | --- |
| tenant(30) × status(6)（有界） | **180**（10万リクエストでも増えない） |
| tenant × **robot_id**（高カーディナリティ・cap 無し） | **100000**（リクエストの種類だけ増える＝爆発） |
| 同上を cap=1000 で | **1000**（超過は `__over__` に畳む） |

- **robot_id / command_id / URL パス全体 / エラーメッセージ本文** はラベルにしない（爆発する）。
- ラベルは **tenant・status・種別（command type）** のような**値の種類が有界**なものだけ。
- 個体を追いたいときはメトリクスでなく**ログ/トレース**に載せる（メトリクスは集計、ログは個別）。
- 最後の安全弁として**カーディナリティ上限**（`metrics.NewLabeled(cap)`）を入れ、超過は `__over__` に
  畳む。監視基盤（Prometheus 等）は系列ごとにメモリ・スクレイプ負荷がかかるので、爆発は事故。

## 記録コストは気にしなくてよい

実測: `Inc` ≈ 90ns、`Observe` ≈ 18ns。**DB 往復（[EXP-31](capacity.md) で ~100,000ns〜）に比べ
桁違いに安い**。「メトリクスを取ると重い」は基本，杞憂。重いのは記録でなく**系列数**（メモリ）。

## トレース（web→worker）

- リクエスト境界で trace/correlation ID を発行し、Web→（DB 経由の）Worker まで引き回す
  （命令行に `trace_id` を持たせる等）。1リクエストが複数コンポーネントをまたぐので、ID が無いと
  追えない。実装は本実験の対象外（ここはラベルとコスト）。

## まとめ

- RED を境界で。プール/キューは USE も。
- ラベルは有界（tenant・status・種別）。高カーディナリティはログ/トレースへ。
- カーディナリティ上限を保険に。記録コストは無視してよい（気にするのは系列数）。

## 保証しない範囲・未検証

- ns/op はこのホストのもの（桁が要点）。本番の監視基盤の負荷は系列数とスクレイプ頻度に依る。
- 分散環境では各レプリカの系列が合算される。ラベル設計は全レプリカ横断で効く。
- トレースの伝播・サンプリングは本実験外。
