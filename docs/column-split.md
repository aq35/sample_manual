# 列を絞る・メモ列を別表に分ける（EXP-19）

「列を押さえた方がいい？」への実測の答え。とくに **失敗理由をメモする大きな列**
（`detail` / `reason`）を一覧行に同居させるか、別表に分けるか。

実験は [internal/splitlab](../internal/splitlab)。receipt は
[docs/results/exp-19](results/exp-19/exp-19-column-split.md)。

## 凍結した仮説

1. 同居のコストは「走査する行数 × 行の太さ」。1 ページ（LIMIT 100）だけなら走査が
   少ないので差は小さい。
2. テナント全体を走査する集計では、太い行（メモ同居）の clustered index はページ数
   が多く、狭い表より明確に遅い（メモを取らなくても）。
3. メモが要る画面では、分割版は「一覧＋id 群のメモをバッチ取得」（DataLoader 相当）
   で足りる。

## 結果（20 万行 / メモ約 3KB / MySQL 8.0）

| ケース | 同居（inline） | 分割（split） | 差 |
| --- | --- | --- | --- |
| 1 ページ一覧（LIMIT 100・メモ取らない） | 1.06ms | 0.77ms | ~1.4x（走査が少ないので小さい） |
| **全体走査の集計（COUNT・メモ取らない）** | **967ms** | **71ms** | **~13.7x** |
| メモが要る画面（1 ページぶんメモも取る） | 1.21ms（1 クエリ） | 2.41ms（一覧＋バッチ） | 分割は往復増えるが 1 ページぶん |

決定的なのは 2 行目。メモを**取らない**集計でも、太い行は clustered index の
ページ数が多く、全走査で 13.7 倍遅い。行の太さは「その列を SELECT するか」と無関係
にスキャン全体へ効く。

## 指針

- **一覧・集計で舐める表は狭く保つ**。大きなメモ（失敗理由・ペイロード）は別表
  （同じ `(tenant_id, id)`）へ出す。一覧は狭い行だけを読むので速い。
- メモが要る画面は「一覧を引く → 見えている id のメモだけをまとめて 1 クエリ」
  （DataLoader / IN バッチ）。往復は増えるが 1 ページぶんだけ。N+1 にはしない。
- **GraphQL でも同じ**：要求されたスカラーだけを投影し、`SELECT *` にしない。
  メモ/理由は別表＋別リゾルバのバッチ取得（DataLoader）にする。フィールドを足す
  たびに一覧クエリが太らないようにする。

## 保証しない範囲・未検証

- 絶対値はバッファプールに載った状態のもの。ディスクから読む状況では差が広がる。
- メモのサイズ・1 ページ件数で差は動く。`TEXT`/`BLOB` は別ページ格納でさらに差が
  出る。
- 分割は書き込みが 2 表になる（一覧行とメモを両方入れる）。整合はトランザクション
  で取る。
