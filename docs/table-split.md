# テーブル分割・パーティションと UPDATE 競合（EXP-15）

- 実験: `internal/contentionlab` / 結果: [docs/results/exp-15/exp-15-table-split-contention.md](results/exp-15/exp-15-table-split-contention.md)

## 何が減って、何が減らないか

| 場合 | 結果 |
| --- | --- |
| 単一文 UPDATE: 幅広い行（状態+大ペイロード同居） | 20,255/s |
| 単一文 UPDATE: 狭い行（熱い状態だけ・ペイロード別表） | **26,078/s（+28.7%）** |
| 行ロック競合（2行を16並行で奪う・tx保持）: 幅広い行 | lock待ち **1,134** |
| 行ロック競合: 狭い行 | lock待ち **1,194（ほぼ同じ）** |
| 履歴掃除: DELETE（1万行） | 97ms |
| 履歴掃除: DROP PARTITION（1万行） | **10ms（約10倍速い）** |

### 効くもの
- **熱い状態を狭い表に分ける** → 1文あたりのコストが下がり、スループット +28%。
  大ペイロード同居は「UPDATE のたびに大きな行を書き直し・二次索引を保守」する。§4.4 の分割は正しい。
- **追記履歴はパーティション** → 掃除が `DROP PARTITION` で桁違いに速い。`DELETE` は undo/purge を作る。
  ただしパーティションキー（日付）が検索条件に入らないと pruning が効かず**逆に重くなる**。

### 効かないもの
- **行ロック競合はテーブル分割では減らない**（ロックは行単位）。同じ行を奪い合う限り、
  wide でも narrow でも待ちは同程度（1,134 vs 1,194）。競合は**主キー設計と書き込みの分散**で解く。

### テナントで割るのは（30 では）増やす
- テナントごとにテーブル/スキーマを割ると、マイグレーション×テナント数・cross-tenant 管理崩壊で**運用負担が増える**。
  30 テナントは `(tenant_id, robot_id)` 先頭 PK の1表で十分（EXP-7）。物理分離が要るコンプラ要件のときだけ。

**結論**: テーブル分割は「**アクセスパターンで分ける**」もの（熱い更新／追記履歴／めったに変わらない を分ける）。
行ロック競合や1文スループットの特効薬でも、テナントで割るものでもない。
