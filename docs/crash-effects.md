# EXP-1 外部 effect の途中で落ちる — 二重送信と「結果不明」

再現:

```bash
eval "$(./scripts/mysql-up.sh --export)"
go test ./internal/effectlab/ -run TestEXP1 -v -timeout 20m
```

結果ファイル: [`docs/results/exp-1/20260903-131939-external-effect-crash.md`](results/exp-1/20260903-131939-external-effect-crash.md)
（実行 SHA・MySQL の設定・全カウンタはこちらに入っている）

---

## 1. 何が問題か

外部サービスを呼ぶ処理の途中でプロセスが落ちると、**「effect が起きたかどうか」が分からない**。
このとき、次の3つは**全部別物**なのに、実装ではよく1つにまとめられてしまう。

| こちらが知っていること | 正しい扱い |
| --- | --- |
| まだ送っていない | 送ってよい |
| 送ったが結果が分からない（timeout・接続断・500） | **送り直す前に確かめる** |
| 相手が受領書を発行した | 完了 |

**timeout を「effect なし」として扱うと、二重送信になる。**
逆に「たぶん起きた」として扱うと、起きていない処理が完了になる。

## 2. 状態の持ち方

```
NOT_STARTED            まだ何もしていない
DISPATCH_RESERVED      送ると決めて記録した（送ったかどうかは分からない）
OUTCOME_UNKNOWN        送ったが結果が分からない  ★これを「失敗」にしない
CLAIMED_SUCCESS        相手が成功と言った（受領書あり）
INDEPENDENTLY_OBSERVED 別経路で effect の存在を確認した
COMPLETED              受領書を持って完了
```

実装で禁止していること（テストで検査している）:

- **timeout や例外を「effect なし」として扱う** → `OUTCOME_UNKNOWN` にする
- **エラー文字列を受領書として保存する** → `receipt_id` には相手が発行した ID しか入れない
  （`last_error` は別列。記録は残すが、状態遷移の根拠にはしない）
- **戻り値だけで完了にする** → `COMPLETED` への更新は `receipt_id IS NOT NULL` を条件にする
- **`OUTCOME_UNKNOWN` を自動で送り直す** → まず相手に問い合わせる

## 3. 実験の作り

- 外部サービスは代役（`internal/effectsvc`）。**effect の記録はサービス側のファイルに fsync** する。
  アプリを SIGKILL しても、外の世界に起きた事実は消えない
- アプリは子プロセス（`cmd/effectlab`）。**7つの地点で自分に SIGKILL** する
- 「effect 成立後・応答前」の地点だけは、サービス側の hook が子プロセスを kill する。
  外から時間で殺すと、effect の前か後かが実行ごとに変わってしまうため
- そのあと**再起動して回復処理**を走らせ、外の effect 回数とアプリの状態を突き合わせる

判定は **DB の中身ではなく、外部サービスの effect 記録**で行う。

## 4. 結果

7地点 × 5要求 × 4方式。数字は7地点の合計。

| 方式 | 二重 effect | 実体の無い完了 | 観測で決着 | 再送 |
| --- | --- | --- | --- | --- |
| naive（呼んでから記録・キー無し） | **5** | 0 | 0 | 0 |
| 冪等キー（送る前に意図を記録） | 0 | 0 | 0 | 0 |
| transactional outbox | 0 | 0 | 0 | 0 |
| outbox + 観測してから決める | 0 | 0 | **5** | 0 |

### 決定的な比較: 相手が冪等キーを守らない場合

| 方式 | 二重 effect |
| --- | --- |
| 冪等キー | **3**（事故に戻る） |
| 観測してから決める | **0** |

> **冪等キーは「相手の保証」であって、こちらの防御ではない。**
> 相手が守るかどうかを検証できない限り、
> **「結果が分からないものは、送り直す前に相手に聞く」**が唯一こちら側で完結する手段。

## 5. なぜ naive が二重になるか

naive は「呼んでから記録する」形（実装でよくある）。
effect が成立してから記録するまでの間に落ちると、**アプリ側には何も残らない**。
再起動後、その要求は「まだ処理していない」ように見えるので、もう一度送る。

**記録を先に、送信を後に**するだけで、少なくとも「送ったかもしれない」ことは残る。
これが `DISPATCH_RESERVED` の意味。

## 6. 適用範囲と未検証

**この結果が当てはまる範囲**

- MySQL 8.0 / 同一ホスト / 外部サービスは同一マシンの HTTP サーバ
- 1プロセス・逐次処理（並行実行時の競合は EXP-2 で扱う）
- 外部サービス側は effect を fsync して記録する（相手の耐久性は仮定している）

**保証しないこと**

- ネットワーク分断（応答が返らないまま接続だけ生きる）は未再現
- 外部サービスが effect 記録の前に落ちる場合は未検証
- 観測 API が古い値を返す（レプリカ遅延）場合の扱いは未検証。
  **観測が「まだ見えていない」と答えたときに送り直すと、二重になりうる**
- 相手に観測 API が無い場合はこの方式が使えない。その場合は
  「相手の冪等性を契約として確認する」か「人が確認する」しかない
