# キャッシュの無効化（EXP-46）

読みをキャッシュすれば DB 負荷は下がるが、書き込み後に **古い値(stale)** を返す危険が出る。
「どれだけ DB を減らせるか」と「どれだけ stale を返すか」は trade-off で、データの stale 許容度で
戦略を選ぶ。さらに期限切れ直後の **一斉読み(stampede)** は singleflight で1回に畳む。

実装は [internal/cachelab](../internal/cachelab)、receipt は
[docs/results/exp-46](results/exp-46/exp-46-cache-invalidation.md)。

## 結果（論理時計 100 step・TTL=10・書込 3 回）

| 方式 | DB 読み | stale を返した回数 |
| --- | --- | --- |
| 無キャッシュ | 100（毎回） | 0（常に新鮮） |
| TTL(10) | **10** | **5**（書込後 ttl まで古い） |
| イベント失効 | **4** | **0** |

- **無キャッシュ**は常に新鮮だが毎回 DB を叩く。
- **TTL** は DB 読みを 100→10 に激減させるが、書き込み後 TTL が切れるまで古い値を返す（5 回）。
- **イベント失効**（書き込みで無効化 → 次の読みで1回だけ引き直す）は DB 読み 4 回・stale 0。
  「新鮮さ」と「DB 負荷」を両立できるが、**書き込みを確実に無効化へ届ける**のが前提。

### stampede（期限切れ直後の一斉読み300）

| | DB 読み |
| --- | --- |
| singleflight なし | 300（全員が引き直す） |
| singleflight あり | **1**（in-flight に合流） |

- 期限切れの瞬間に 300 が一斉に読むと、素朴には 300 回 DB を叩く（キャッシュが効かない一瞬に
  負荷が集中）。`golang.org/x/sync/singleflight` で同キーの引き直しを1回に畳める（[EXP-38](sse-fan-in.md)と同じ）。

> 計測の落とし穴: load が即返る実装だと goroutine が in-flight に重ならず「300→299」のような
> 嘘の結果になる。本実験は全 goroutine が到着してから一斉に解き放ち、load を少し待たせて
> 本物の一斉読みを再現した（そうして初めて 300→1 に畳めることが見える）。

## 要点

- **stale 許容度で選ぶ**。残高・在庫のように古い値が許されないものは無キャッシュかイベント失効。
  表示名・集計のように数秒古くてよいものは TTL でよい。
- **併用が実務的**：短めの TTL（上限保証）＋イベント失効（早く新鮮に）。TTL だけだと最大 ttl ぶん
  古く、イベント失効だけだと無効化の取りこぼしが怖い。両方で保険をかける。
- **stampede は singleflight で畳む**。期限切れ・キャッシュ起動直後の一瞬に効く。
- 書き込みの無効化は、同プロセスなら簡単（メモリのフラグ）。プロセスを跨ぐなら pub/sub で
  無効化イベントを配る（[EXP-43](sse-fan-in.md) と同じ経路）。

## 保証しない範囲・未検証

- 実際の stale 許容はデータ次第。本実験は「DB 読み回数」と「stale を返した回数」の trade-off を
  論理時計で示すもので、絶対時間や実 DB のレイテンシは測っていない。
- イベント失効は「書込を確実に無効化に届ける」のが前提。届かない（取りこぼす）と stale が残る。
- 部分無効化（一部キーだけ失効）・キャッシュの容量制御（LRU 追い出し）は本実験外。
