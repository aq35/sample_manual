# 共有ワーカーのテナントスコープ強制（EXP-58）

共有ワーカー（1プロセスが全テナントを回す）の安全は、**プロセスを分けること**でなく
**全クエリにテナント境界を強制すること**で決まる。境界を **1本書き忘れるだけ**で、
他テナントの行を**読み**（情報漏洩）・**書き**（データ破壊）してしまう。これを実測した。

実装は [internal/scopelab](../internal/scopelab)、receipt は
[docs/results/exp-58](results/exp-58/exp-58-tenant-scope-enforcement.md)。
設計判断は [worker-tenancy](worker-tenancy.md)、境界の機械強制は [security-layers](security-layers.md)。

## 結果（共有表に tenantA・tenantB 各 100 行。A の処理を実行）

| 操作 | スコープ強制あり（`WHERE tenant_id=?`） | 書き忘れ（`status` だけで絞る） |
| --- | --- | --- |
| **読み** | A の 100 行だけ。**他テナント=0** | B の **100 行まで読める**（情報漏洩） |
| **書き（done 化）** | A の 100 行だけ。**他テナント破壊=0** | B の **100 行まで done**（データ破壊） |

- **強制あり**: `SELECT/UPDATE ... WHERE tenant_id=? AND ...` → テナント A の処理は A の行しか触らない。
  **cross-leak = 0**。
- **書き忘れ**: `... WHERE status='pending'`（テナント境界なし）→ B の行まで見え、B の行まで更新した。
  **cross-leak = 100**（＝同居する他テナント全部）。1行の書き忘れが全越境になる。

## 要点

- **共有ワーカーの分離はコードで作る**。プロセスを分けなくても、全クエリに `tenant_id=?` を
  強制すれば越境は 0。逆に、プロセスを分けても**1本の生 SQL で境界を書き忘れれば越境する**。
- **人手で毎回書かない。機械で強制する**：
  - `repo.Scope` が `:tenant` を**自動注入**し、テナントは **ctx から**取る（クライアント入力を信じない）。
  - 生 SQL は `sqllint`（rawdb / layerimport）で**禁止**して、スコープを迂回できないようにする（[static-analysis](static-analysis.md)）。
- **プロセス分離は「最後の砦」**。上記を全テナントに効かせたうえで、高感度テナントだけ
  プロセス／DB 資格情報を分けてブラスト半径を物理的に限定する（[worker-tenancy](worker-tenancy.md)）。

## なぜ「1本の書き忘れ」がここまで効くか

共有表には**全テナントの行が同居**している。テナント境界は**その行の中の `tenant_id` 列**でしか
表現されない。だから `WHERE tenant_id=?` を落とした瞬間、クエリは「同居する全テナント」を対象にする。
書き込み（UPDATE/DELETE）なら、他テナントのデータを**取り返しのつかない形で壊す**。
「越境は 0 か 全部か」——中間が無いのが怖いところ。

## 保証しない範囲・未検証

- ここは境界の**有無だけ**を見た（processing テナントは固定）。実コードではテナントを ctx から取り、
  `repo.Scope` が注入する。
- 読みの越境は「見えた行数」、書きの越境は「done にした行数」で測った。実害はデータの中身次第で更に大きい。
- 物理分離（schema-per-tenant / DB-per-tenant）は本実験の対象外（行レベル分離＋スコープ強制が主軸）。
