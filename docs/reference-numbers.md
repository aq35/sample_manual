# 正規化した早見表（設計の当たりを付ける数値）

各実験で実測した「単価」を1枚に集めた早見表。**絶対値でなく単価と桁で見る**（ns はこの
サンドボックス CPU のもので本番と違う。バイト・alloc・走査行数は環境に依りにくい）。
出典の receipt を各節に付けた。スケーリングは末尾の公式で。

> 具体的なイメージが欲しいときは、この単価に数字を代入した **[Worker/Web 単体の実寸サンプル
> （メモリ・CPU の圧迫を計算＋図で）](worked-examples.md)** を先に見ると分かりやすい。

## 1. Go のメモリ単価（[EXP-50](../internal/memlab) / [receipt](results/exp-50/exp-50-memory-unit-cost.md)）

### 静的サイズ（変数そのものの幅・`unsafe.Sizeof`）

| 型 | バイト | 備考 |
| --- | --- | --- |
| `int64` / `float64` / ポインタ | **8** | 参照はすべて 8B（64bit） |
| `bool` / `byte` | 1 | struct 内ではアラインで膨らむ |
| `string` ヘッダ | **16** | ptr(8)+len(8)。**本体は別ヒープ** |
| `[]T` スライスヘッダ | **24** | ptr(8)+len(8)+cap(8)。本体は別 |
| `struct{ID int64; Tenant int32; Flag bool}` | **16** | 8+4+1=13 → 16 にアライン |
| 一覧行 struct（int64×2 + string×2） | **48** | 文字列本体は含まない |
| `struct{}`（空） | **0** | 集合の値・シグナルに最適 |

### 実確保のヒープ増分（1個あたり・ヘッダ/アライン/バケット込み）

| 確保するもの | 1個あたり | 読み |
| --- | --- | --- |
| `[]int64` の要素 | **8B** | 連続・ムダなし |
| `[]*int64`（各要素を別確保） | **16B** | ヘッダ 8 + 指す先 8。ポインタの海は倍食う |
| `[]SmallStruct`（値・連続） | **16B** | 値で持つと連続＝キャッシュも効く |
| 文字列**リテラル**（同じ値） | **16B** | ★本体を共有。per-row はヘッダだけ |
| 文字列（DB から読んだ別本体・~13B） | **32B** | ヘッダ16 + 本体（16 の size class） |
| `map[int64]int64` のエントリ | **~38B** | 要素 16B より重い（バケットのオーバーヘッド） |
| goroutine スタック（park 中） | **~2KB** | 初期スタック。EXP-31 の「接続下限 2.6KB」と整合 |

### 予算 1.2GB（2GB のうち接続/データに使える枠）に載る個数

| もの | 理論上限 | 実運用の目安（安全率 1/2〜1/3） |
| --- | --- | --- |
| `int64` | ~1.6 億 | — |
| 値 struct（16B） | ~8000 万 | — |
| 文字列（別本体 32B） | ~4000 万 | — |
| map エントリ | ~3400 万 | — |
| goroutine（＝常時接続の下限） | ~63 万 | **SSE は 1万〜1.5万本**（EXP-31。TLS バッファ込み） |

> **要点**: 「2GB あるから無限」ではない。**1件の単価 × 件数が予算を超えれば OOM**。
> 見積もりは単価 × 件数、実運用は単価の 2〜3 倍（GC 余白・突発確保）を見込む。

## 2. ループとアロケーションの単価（[EXP-51](../internal/looplab) / [receipt](results/exp-51/exp-51-loop-alloc-cost.md)）

n=10000 を組む1回あたり。**ns は相対、allocs/op と B/op を主に読む**（GC 圧の指標）。

| やり方 | ns/op | allocs/op | B/op | 対策版比 |
| --- | --- | --- | --- | --- |
| `append`（nil から・事前確保なし） | 151µs | **19** | 358KB | 基準（悪い） |
| `append` + `make([]T,0,n)`（事前確保） | 33µs | **1** | 82KB | **~5x 速・alloc 1/19** |
| `make([]T,n)` + 添字代入 | 35µs | 1 | 82KB | 同上 |
| 文字列 `+=`（O(n²) バイト） | **29ms** | **10000** | **53MB** | 基準（最悪） |
| 文字列 `strings.Builder` | 68µs | 16 | 47KB | **~424x 速・B/op 1/1000** |
| `map` サイズ未指定（rehash） | 803µs | 79 | 591KB | 基準 |
| `map` + `make(map,n)` | 292µs | 33 | 296KB | **~2.7x 速** |
| `int` を `any` に積む（boxing） | 244µs | **9745** | 242KB | 基準（悪い） |
| 型つき `[]int` に積む | 28µs | **1** | 82KB | **alloc 1/9745** |
| ループ本体の素コスト（要素を1回触る） | — | 0 | 0 | **1件 ≒ 0.64ns** |

> **要点**: 同じ結果でも確保の仕方で **ns も alloc も桁で変わる**。
> - 件数が読めるなら `append` は `make(,0,n)` で事前確保（再確保コピーを消す）。
> - 文字列連結は `+=` でなく `strings.Builder`（`+=` は O(n²) バイト）。
> - `map` は `make(map,n)` でサイズを伝えて rehash を避ける。
> - ホットパスで `int`→`any` を作らない（boxing が要素数ぶん確保を生む）。
> - **`allocs/op` を減らすのが GC 圧を下げる最短路**。ループ本体自体は 1件 ~1ns で、
>   実処理は次章の **DB 往復（0.1ms〜）が支配的**＝1件で素ループの数千倍。

## 3. DB 往復と走査の単価（[EXP-31](capacity.md) / [EXP-18](date-search.md) / [EXP-21](column-projection.md)）

### DB 往復/秒（同ホスト MySQL・往復 ~0.1ms）

| 並行度 | 1 | 4 | 16 | 32 |
| --- | --- | --- | --- | --- |
| 往復/秒 | 10k | 26k | 46k | 54k |

本番は RTT が効く（外挿）:

| 往復遅延 | 並行度 8 | 並行度 16 |
| --- | --- | --- |
| 0.5ms | ~16k 件/秒 | ~32k 件/秒 |
| 2ms | ~4k 件/秒 | ~8k 件/秒 |

### クエリは「総行数」でなく「走査行数」で重くなる（[EXP-18](date-search.md)・1M 行 covering）

| 走査行 | p50 | 読み |
| --- | --- | --- |
| 274（1日・10万行） | 0.7ms | index で当たった分だけ |
| 2,740（1日・100万行） | ~1.8ms | 総行数が増えても走査は同じ |
| 35,820（7日） | ~13ms | 走査に比例 |
| 154,172（30日） | 50ms超 | 走査が増えれば線形に重い |

### 列幅とクエリ劣化（[EXP-21](column-projection.md)・全体走査 COUNT）

| 行の形 | p50 | 読み |
| --- | --- | --- |
| narrow（太い列なし・基準） | **11ms** | — |
| VARCHAR 3KB（inline） | 117ms | **太い列を inline で持つと舐めが 10 倍重い** |
| TEXT 3KB（inline） | 147ms | 型名でなく inline かどうか。TEXT でも軽くならない |
| TEXT 24KB（off-page） | 11ms | 大きいほど外へ出て、舐め自体は軽い |
| ↑を `SELECT *` で本体も取る | **170ms** | **1行ごとに off-page を取りに行き最悪** |

> **要点**: 「重いクエリ」は **走査行数 × 行の幅 × 取りに行く列**。covering index で走査を絞り
> （[EXP-18](date-search.md)）、太い列は別表 or off-page にし（[EXP-19](table-split.md)/[EXP-21](column-projection.md)）、
> `SELECT *` を避けて必要列だけ射影する（[EXP-21](column-projection.md)）。実行前に走査見込みで弾く
> コストゲートは [EXP-7/query-cost-gate](query-cost-gate.md)。

## 4. 1 vCPU / 2GB タスクの理論値（[EXP-31](capacity.md)）

上の単価から出した1タスクの目安。**律速が種類ごとに違う**のが要点。

| 種類 | 律速 | 目安（1タスク） | 増やし方 |
| --- | --- | --- | --- |
| **SSE 常時接続** | メモリ・fd | **1万〜1.5万本**（安全率込み。理論上限は数十万） | 横（レプリカ）・DB は共有ハブ、1:1 で接続を持たせない |
| **Worker 処理** | DB プール×往復遅延 | 本番往復で **数千〜数万件/秒** | 横（レプリカ）＋ batch。合計接続は [poolbudget](../internal/poolbudget) で天井確認 |
| **Web rps** | CPU（＋DB プール） | モデル `rps ≒ 1000ms ÷ 1req の CPU ms`（5ms→200rps）。**実機で測る** | 縦 or 横。同時実行は CPU と DB プールの小さい方で頭打ち（[EXP-5](pool-saturation.md)） |

- **1タスクを大きくするより横に割る**（GC 停止・障害影響・接続予算のどれも有利・[EXP-30](redundancy.md)）。
- どこまで増やしても最後の天井は **DB の接続予算と DB 自体**。

## 5. 使い方（スケーリング公式）

```
接続で載る本数   ≒ 接続予算(≈1.2GB) ÷ 1接続メモリ(TLS 込み ~34KB) → 実運用はその 1/2〜1/3
メモリに載る件数 ≒ 1.2GB ÷ (1件の単価 × 安全率2〜3)
Worker 処理量    ≒ プール並行度 × (1 / DB往復遅延) × batch係数
Web rps          ≒ 1000ms ÷ 1リクエストの CPU 時間(ms)   ※ I/O 待ち中は重ねられる
クエリの重さ     ∝ 走査行数 × 行の幅 × 取りに行く列（総行数ではない）
GC 圧            ∝ allocs/op × 頻度（B/op でなく回数が効く）
```

- **数字は設計の当たり付け**。最後は必ず **1 vCPU/2GB の実機**で p95 と rps を測る。
- 迷ったら **横に割る・単価を下げる・走査を絞る・alloc を減らす** のどれか。

## 保証しない範囲・未検証

- ns/rps はこのサンドボックス CPU のもの（本番と違う）。**桁と単価**で使う。
- メモリ単価は Go バージョン・GC・アロケータで上下（オーダーで使う）。RSS はこれ＋ランタイム余白。
- DB 往復/秒は同ホスト。本番は RTT 次第（表は往復遅延を仮定した外挿）。
