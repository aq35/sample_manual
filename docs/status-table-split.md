# ステータスでテーブルを分けるべきか（EXP-22）

pending / queued / 進行中 / 完了 / 失敗 / キャンセル——状態ごとにテーブルを分けた方が
速い？ 今は全部1テーブル。実測で答える。

実装は [internal/statuslab](../internal/statuslab)。receipt は
[docs/results/exp-22](results/exp-22/exp-22-status-table-split.md)。

## 結論：状態でテーブルを分けるな。索引で絞れ。

状態は**遷移で動く**（pending→queued→進行中→完了）。テーブルを状態で分けると、
状態が変わるたびに別テーブルへ引っ越し（DELETE+INSERT）が要る。分ける鍵ではなく、
**索引で絞るもの**。

## 結果（20万行・うち直近 1% が active / MySQL 8.0）

### ① pending を古い順に1ページ取る（worker の定番クエリ）

| 方式 | p50 |
| --- | --- |
| 1テーブル ＋ status 索引 | **462µs** |
| 1テーブル・索引なし（全表走査） | 76ms（約 **165x**） |
| hot 表（active だけを隔離） | 466µs |

- `(tenant_id, status, id)` の索引があれば、terminal が 99% 溜まっていても **狙い撃ち**
  で速い。
- **1テーブル索引（462µs）≒ hot 表（466µs）**。索引が効くなら、分割しても pending
  抽出は速くならない。→ この用途で分割は不要。
- 索引が無いと、古い terminal を大量に舐めて **165x** 遅い。効くのは分割ではなく索引。

### ② 状態遷移のコスト

| 方式 | 1遷移あたり p50 |
| --- | --- |
| 1テーブルで `UPDATE` 一発 | 1.05ms |
| 別テーブルへ引っ越し（`DELETE`+`INSERT`・要トランザクション） | 1.66ms（約 1.6x） |

状態で分けると、遷移のたびに 2 表への書き込み＋2 索引更新＋トランザクションになる。
状態は頻繁に変わるので、この差は積み上がる。しかも失敗時に「消えた／二重」の事故余地
が増える。

### ③ 終端行が溜まると効くもの（全体走査）

| 操作 | p50 |
| --- | --- |
| 全体 COUNT（terminal 込み・1テーブル） | 63ms |
| 全体 COUNT（active だけの hot 表） | 0.95ms（約 66x） |

pending 抽出（①）は索引で速いままなので、terminal が溜まっても困らない。困るのは
**テーブル全体を舐める操作**（全体集計・非索引の探索）。ここで初めて hot/cold 分離が
効く。

## 指針（この順で）

1. **status に索引を張る**（`(tenant_id, status, id)`）。まずこれ。1テーブルのまま
   pending 抽出は速い。
2. **状態ごとの分割はしない**。遷移が引っ越しになって重く、事故りやすい。
3. 全体走査・掃除が重くなってきたら、**状態でなく hot/cold で分ける**：終わった行
   （done/failed/cancelled）をアーカイブ表へ移す。動く行の表は小さく保たれる。
4. 履歴が巨大なら**時間でパーティション**して古いのを丸ごと捨てる。`DROP PARTITION`
   は `DELETE` の 10x 速い（[EXP-15](table-split.md)）。

子テーブル（小タスク）を分けているのは別の話で、正しい正規化。状態分割とは無関係。

## 保証しない範囲・未検証

- 索引ありの pending 抽出が terminal 量にほぼ依らないのは索引シーク前提。
- 掃除（terminal の削除）は本実験外。DELETE vs DROP PARTITION は [EXP-15](table-split.md)。
- 分割の別の代償（結合・二重書き込みの整合・移行）は本実験の対象外。
- 絶対値はバッファプールに載った状態のもの。
