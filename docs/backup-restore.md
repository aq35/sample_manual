# バックアップ・復元・破損（EXP-11）

- 実験: `internal/backuplab` / `MYSQL_DSN=... go test ./internal/backuplab/ -run TestEXP11 -v`
- 結果: [docs/results/exp-11/20260903-150721-backup-restore-corruption.md](results/exp-11/20260903-150721-backup-restore-corruption.md)
- 実行 SHA は結果ファイルの先頭にある

## この文書の一行め

**「バックアップコマンドが成功した」を成功条件にしない。**

`mysqldump` は、書いている途中でも・切れても・古くても、終了コード 0 を返す。
「取れた」を信じると、**戻せないバックアップを保管し続ける**ことになる。

成功条件はこう置いた。

> データを書く → バックアップ → 元を壊す → **別の環境**へ復元 →
> スキーマの指紋を突き合わせる → **中身のハッシュ**を突き合わせる（行数ではなく）→
> アプリを起動して lease・robot_state・マイグレーション状態を読み戻せる

## 指紋（何をもって「同じ」とするか）

`backuplab.Fingerprint` は3つを持つ。

1. **スキーマ定義のハッシュ** — `information_schema.columns` から、表・列・型・NULL 可否・
   既定値・キー・extra を畳んだもの。**`schema_migrations` の記録ではなく実物の表**を見る
2. **表ごとの中身のハッシュ** — 列を `information_schema` の順に並べ、行を主キー順で読んで畳む。
   NULL と空文字を区別する
3. **`schema_migrations` の内容** — version・checksum・state

`Equal` は一致しなければ**理由を文で返す**（「表 X が無い」「表 X の中身が違う（行数 a → b）」
「スキーマが違う」「適用済みマイグレーションが違う」）。

★**行数では判定しない。** 行数が同じで中身が違う復元は、いちばん静かな失敗だから。

## 結果

| 場合 | どう壊したか | 結果 |
| --- | --- | --- |
| 正常系 | `--single-transaction` で取り、別環境へ復元 | 指紋一致・**アプリ起動 OK**（robot_state 200 件 / lease owner・fence を読み戻せた） |
| 切れたバックアップ | 末尾 40% を捨てた | 復元が SQL 構文エラーで**失敗** → 拒否できる |
| **古いバックアップ** | 取った後に**値だけ**変えた（行数は不変） | **行数一致・指紋不一致**。中身のハッシュだけが違いを捉えた |
| スキーマ違い | `robot_profile` を含めずに取った | 指紋が「表 robot_profile が無い」で拒否。ただし**アプリは起動してしまう** |
| バイト破損 | 中ほどの1バイトを反転 | 復元は通ったが、指紋不一致（robot_state の中身が違う。行数 1703→1703） |

### 古いバックアップ ― 行数では見分けられない

バックアップを取った後、元の環境で `battery` の値だけを変えた（行の増減なし）。

- **行数**: 一致（完全に同じ）
- **指紋**: 不一致（`表 robot_state の中身が違う`）

行数を成功条件にしていたら「同じ」に見える。
中身のハッシュだけが、古い断面であることを捉える。

### スキーマ違い ― アプリの起動は成功条件にならない

`robot_profile` を含めずに取ったバックアップを復元し、アプリを起動した。

- `schema_migrations` は `0003` まで『済』と記録している
- `repo.Migrate` はその記録を見て「当たっている」と判断し、**何もしない**
- アプリが起動時に読むのは `robot_state` と `lease` だけなので、**起動は成功する**

つまり「起動できた＝復元できた」を信じると、`robot_profile` を最初に触った瞬間に本番で落ちる。
**実物の表を指紋で見て初めて**、`robot_profile` の欠落が分かる。
これは EXP-6（マイグレーションは記録ではなく実物で判断する）と同じ教訓の別の現れ。

## 別環境への復元

復元先は `DROP DATABASE` を使わず、**対象の表だけを落としてから**流し込む
（`backuplab.DropTables`）。テーブル単位の権限しか無い利用者――本番でよくある構成――でも
復元できるようにするため。外部キーの順序を気にせず落とせるよう、
一時的に `foreign_key_checks` を切る。

この実験の「別環境」は同一サーバの別スキーマ（`workerdb` → `workerdb2`）。
`MYSQL_DSN2` を渡せばそちらへ復元する。

## 適用範囲と未検証

**当てはまる範囲**

- MySQL 8.0 / `mysqldump --single-transaction`（InnoDB の一貫した断面）
- 論理バックアップ（SQL テキスト）
- 判定は行数ではなく中身のハッシュ

**保証しないこと（LIVE_ENV_REQUIRED のものを含む）**

- **物理バックアップ**（Percona XtraBackup・EBS スナップショット・LVM）は未検証。
  手順だけ書く: ①書き込み中にスナップショットを取る ②別インスタンスにアタッチ
  ③`crash recovery` が走ることを確認 ④この指紋で突き合わせる ⑤アプリを起動する
- **point-in-time recovery**（フルバックアップ + binlog 適用）は未検証
- レプリカからのバックアップ・GTID の整合は未検証
- BLOB・生成列・トリガ・ビューを含む表の指紋は未検証（このアプリには無い）
- 別ホスト・別バージョンの MySQL への復元は未検証

## 再利用できる成果物

- `internal/backuplab`: 取る／戻す／壊す（切る・バイト反転）／指紋を突き合わせる。
  指紋は行数ではなく中身のハッシュ。他プロジェクトの「復元できたか」の判定に流用できる
- `backuplab.Fingerprint.Equal`: 差の理由（スキーマ・表・マイグレーション）を文で返す
- 「別環境へ復元してアプリを起動する」を成功条件にした回帰テスト（`TestEXP11`）

## SQLite との違い

SQLite のバックアップは EXP-10（`docs/sqlite.md`）で別に測っている。
`.db` だけをコピーすると WAL 上のコミットを失う、`integrity_check` が `ok` でも
中身が同じとは限らない、といった SQLite 固有の罠がある。
**MySQL の結論をそのまま持ち込まない**（EXP-10 の分類を参照）。
