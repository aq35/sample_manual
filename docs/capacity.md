# 1 vCPU / 2GB のタスクでどれくらい捌けるか（EXP-31）

「ECS タスク 1 vCPU / 2GB で、SSE は何本・Worker はどれくらい捌けるか」への見積もり。
結論から: **上限は CPU より先に、メモリ（SSE 本数）と DB（Worker 往復）で決まる**ことが多い。

実装は [internal/capacitylab](../internal/capacitylab)、receipt は
[docs/results/exp-31](results/exp-31/exp-31-task-capacity.md)。

> 「律速」＝一番遅い所が全体の速さを決めること（英: bottleneck）。他の用語は [用語集](glossary.md) へ。
> 具体的な数字のイメージは [worked-examples.md](worked-examples.md)（Worker/Web 単体サンプル）。

## 実測した単位コスト

| 測ったもの | 値 |
| --- | --- |
| 1接続メモリ（goroutine のみ・下限） | 約 **2.6 KB** |
| 1接続メモリ（+ 8KB バッファ） | 約 10 KB |
| 1接続メモリ（+ 32KB バッファ・TLS 現実的） | 約 **34 KB** |
| DB 往復/秒（並行度 1 / 4 / 16 / 32・同ホスト） | 10k / 26k / 46k / 54k |

## SSE は何本つなげる？ → **メモリ律速。現実的に 1万〜1.5万本を上限に設定**

SSE は idle でも 1接続 = goroutine + 読み書きバッファのメモリを食う。2GB のうち
ランタイム/GC/アプリで ~800MB を残し、**~1.2GB を接続に使える**とすると:

```
本数 ≒ 接続予算 ÷ 1接続メモリ
下限バッファ:  1.2GB ÷ 2.6KB ≒ 47万本（非現実的な理論値）
TLS 現実的:    1.2GB ÷ 34KB  ≒ 3.6万本
```

- **実運用は理論値の 1/2〜1/3 を上限に**（GC 余白・突発確保・安全率）。→ **1万〜1.5万本**が無難。
- **鉄則: SSE 1本に DB 接続を1:1で持たせない**。持つと接続予算（[EXP-5](pool-saturation.md)）で
  すぐ枯れる（1 vCPU タスクの DB プールはせいぜい数十本）。更新の push は**共有ハブ**（in-memory）
  から配り、DB は必要なときだけ小さい共有プールで触る。
- **fd 上限（ulimit -n）を上げる**こと。1万接続なら nofile を 65536 以上に。
- 死んだ接続を掃除するため**ハートビート/アイドルタイムアウト**を必ず入れる（数万本が幽霊化しない）。

> 1万本を1タスクで抱えるより、**5千本×2〜3タスク**に横で割る方が、GC 停止も障害影響も小さい
> （[EXP-30](redundancy.md)）。SSE は「メモリと fd」で見積もり、横に割る。

## Worker はどれくらい捌ける？ → **DB 律速。CPU はほぼ余る**

Worker の「claim → dispatch」は短い DB 往復の繰り返しで、CPU はほとんど IO 待ち。処理量は:

```
処理量(件/秒) ≒ プール並行度 × (1 / DB往復遅延) × バッチ係数
```

実測は同ホスト DB（往復 ~0.1ms）で並行度 16 → **46k 往復/秒**。本番は往復遅延が効く:

| DB 往復遅延（本番想定） | 並行度 8 | 並行度 16 |
| --- | --- | --- |
| 0.5ms | ~16k 件/秒 | ~32k 件/秒 |
| 2ms | ~4k 件/秒 | ~8k 件/秒 |

- 1 vCPU でも Worker は IO 待ちが主なので**数千〜数万件/秒**は出る。**律速は CPU でなく
  「DB プール本数 × 往復遅延」と DB 自体の書き込み能力**。
- さらに [EXP-12](scheduling.md) のとおり、1回のポーリングで `batch` 件まとめて捌けば
  往復あたりの件数が増える（`処理量 ≒ batch / interval`、ただし DB が受けきれる範囲）。
- Worker のプールは小さく（[EXP-29](web-worker-split.md) の分離ぶん・例: 2〜20本）。それでも
  上記の件数は出る。足りなければ**縦（vCPU/メモリ増）より横（Worker レプリカ増）**——ただし
  合計接続が DB 予算を超えないよう [poolbudget](../internal/poolbudget) で確認（[EXP-30](redundancy.md)）。

## 一般の Web リクエストは？ → **CPU 律速。ターゲットで測る**

JSON 整形・圧縮・TLS ハンドシェイクなど計算主体の rps は 1 vCPU の実機で測るしかない
（このリポジトリのサンドボックス CPU は本番 1 vCPU と違うので、測ると誤解を生む）。モデルだけ:

```
rps ≒ 1000ms(1 vCPU の1秒) ÷ 1リクエストの CPU 時間(ms)
例) 1リクエスト 5ms CPU → 約 200 rps / 2ms → 約 500 rps
```

- I/O 待ち（DB 応答待ち）中は CPU が空くので、実効 rps はこれより高く出る（並行で重ねられる）。
- ただし**プール本数以上の同時 DB クエリは待たされる**（[EXP-5](pool-saturation.md) の膝）。Web の
  同時実行は「CPU」と「DB プール」の小さい方で頭打ち。
- **必ず 1 vCPU/2GB の実機で負荷をかけて p95 と rps を測る**。上の数字は設計の当たりを付ける用。

## まとめ（1 vCPU / 2GB の目安）

| 種類 | 律速 | 目安 | 増やし方 |
| --- | --- | --- | --- |
| SSE 常時接続 | メモリ・fd | **1万〜1.5万本**（安全率込み） | 横（レプリカ）・DB は共有ハブ |
| Worker 処理 | DB プール×往復遅延 | 本番往復で**数千〜数万件/秒** | 横（レプリカ）＋ batch |
| Web rps | CPU（＋DB プール） | 実機で測る（モデル: 1000ms/req-CPU） | 縦 or 横・プールは EXP-5 の膝 |

- **1タスクを大きくするより、横に割る**のが基本（GC 停止・障害影響・接続予算のどれもが有利）。
- どこまで増やしても最後は **DB の接続予算（[poolbudget](../internal/poolbudget)）と DB 自体**が天井。

## 保証しない範囲・未検証

- メモリ実測は Go の HeapAlloc+StackInuse の増分。実際の RSS は TLS 実装・アロケータで上下する。
- DB 往復/秒は同ホスト MySQL のもの。本番は RTT 次第（表は往復遅延を仮定した外挿）。
- CPU 律速 rps は未測定（要ターゲット実機）。上のモデルは当たり付け用。
