## 1. 状態比較のコスト（§8）

`go test ./internal/model/ -bench Compare -benchmem -count=3`
（1,000件のマップから引いて `==` で比較、1回あたり）

| 比較対象 | 実測 | 資料 |
| --- | --- | --- |
| `Status uint8` | **19.96 〜 20.05 ns** | 7.1 〜 7.3 ns |
| `Status string` | **21.24 〜 21.70 ns** | 8.6 〜 9.0 ns |
| `Status string`（同長・末尾1文字違い） | **25.36 〜 26.16 ns** | 10.7 〜 11.1 ns |

**結論は資料と同じ。** 整数型と文字列の差は 1件あたり **約 1.5 ns** で、実質誤差。
**整数型を選ぶ理由は「速いから」ではなく「打ち間違いがコンパイルエラーになるから」**（§6.3）。
`"runing"` は文字列なら通ってしまい、DB の値と永遠に一致せず「変化あり」と判定され続ける。

## 2. JSON の解析（§6.1）

`go test ./internal/jsonx/ -bench Parse -benchmem -count=3`（1,000件・455 KB を1回解析）

| やり方 | 時間 | メモリ | 割り当て回数 |
| --- | --- | --- | --- |
| **要る項目だけの構造体** | **5.35 ms** | **186 KB** | **3,019** |
| 全項目を書いた構造体 | 8.63 ms | 1,227 KB | 13,020 |
| **`map[string]any`** | **9.59 ms** | **2,874 KB** | **66,991** |

- `map[string]any` は要る項目だけの構造体に対して **メモリ 15倍・割り当て 22倍**（資料: 26倍 / 30倍）
- 全項目を書いた構造体でも **メモリ 6.6倍**（資料: 8.3倍）

「将来使うかもしれないから全部定義しておく」は、そのぶん毎回払うことになる。

## 3. 大きい配列の受け取り方（§6.2）

`go test ./internal/jsonx/ -bench Receive -benchmem -count=3`

| 受け方 | 時間 | メモリ |
| --- | --- | --- |
| `io.ReadAll` してから `Unmarshal` | 6.37 ms | **2,724 KB** |
| `Decoder.Decode(&全体)` | 6.07 ms | **1,233 KB** |
| **`Decoder` で配列を1件ずつ** | **5.42 ms** | **107 KB** |
| （参考）WebSocket の1件を `Unmarshal` | 5.7 µs | 320 B |

**25倍の差**（資料は 20倍）。前2つは「本文まるごと ＋ 全件のスライス」を同時に持つ。
A（全件同期）でやりたいのは「1件ずつ記憶と比べる」ことなので、全件のスライスは要らない。

## 7. 負荷シミュレーション（§4.1 の表）

`go run ./cmd/loadsim -rate 1000 -duration 10s -robots 1000 -change-rate 0.01`

| 手 | トランザクション/秒 | 書いた行/秒 | 追いついたか |
| --- | --- | --- | --- |
| 素直に1件ずつ UPDATE | **1000.0** | 1000.0 | **いいえ（10秒の負荷に 15.3秒。遅延 5.3秒）** |
| ① 変化したときだけ書く | **10.7** | 10.7 | はい（遅延 5ms） |
| ② さらに200msバッチ＋重複排除 | **4.2** | 10.7 | はい（遅延 2ms） |

資料の試算（1000 → 10 → 5）と**ほぼ一致**。
加えて分かったこと: **素直に書く方式は、そもそも 1,000件/秒に追いつかない**。
遅延は時間とともに増え続ける（このマシンでは 10秒で 5.3秒の遅れ）。

## 8. MySQL の挙動（§9 の未検証項目）

`go test ./internal/mysqlfacts/ -v`。**MySQL 8.0.46 で確認**。

| 項目 | 結果 |
| --- | --- |
| `innodb_flush_log_at_trx_commit` はサーバ全体の設定か | **そのとおり**。`SET SESSION` は `Error 1229` で拒否される |
| 動的に変更できるか | **できる**（`SET GLOBAL`、再起動不要）。ただし**同じインスタンスの他の業務データにも一律で効く** |
| 0 / 1 / 2 の差 | 1: 693 tx/s ／ 2: 1,044 tx/s ／ 0: 1,148 tx/s（autocommit・1件更新） |
| `AS new`（行エイリアス）が使えるか | **使える**。旧構文 `VALUES(col)` は `Warning 1287`（非推奨） |
| （追加で判明）`AS new` の副作用 | UPDATE 部の**裸の列名が曖昧になる**（`Error 1052`）。既存行側は必ず表名で修飾する |
| 同じ値になる UPDATE を省くか | **省く**。`affected_rows` は 0（新規=1 / 値が変わる更新=1 or 2） |
| （追加で判明）省いても**行ロックは取る** | 別トランザクションは待たされる → **メモリで弾かないと往復もロックも消えない** |
| RANGE パーティションの構文 | `PARTITION BY RANGE COLUMNS(date)` が通る。**生成列はパーティションキーにできない** |
| `DROP PARTITION` と `DELETE` の差 | 5万行で **16 ms vs 206 ms（12.7倍）**。DELETE はこの後 purge も残る |
| 長いトランザクションと undo | History list length が **28 → 2,000** に増える。開いている間は purge されない |
| `MaxIdleConns` の既定値 2 の影響 | 300クエリ（10並列）で新規接続 **199本**。`= MaxOpenConns` にすると **10本** |
| `ConnMaxIdleTime` > `wait_timeout` のとき | 下記のとおり、**症状は「即エラー」ではない** |

### `wait_timeout` で切られた接続の扱い（資料より詳しい結果）

`wait_timeout = 2秒` にして、接続を4秒放置してから使った場合:

| 使い方 | 結果 |
| --- | --- |
| `db.Query` などの単発 | **エラーにならない**。`database/sql` が死んだ接続を捨てて張り直し、再試行する |
| `db.Conn()` で掴んだ接続 | **`Error 4031`（inactivity で切断された）** |
| `db.Begin()` したトランザクション | **`Error 4031`** |

**資料の「使った瞬間にエラーになる」は、条件つきで正しい。**
単発クエリは黙って回復するが、その代金として**毎回再接続が起きる**（TLS 込みだとクエリ本体より高い）。
トランザクションや `sql.Conn` では回復できず、エラーとして露出する。
`ConnMaxIdleTime` を `wait_timeout` より短くすれば、どちらも起きない。

## 9. 実装して初めて分かったこと

資料には書かれていないが、動かしてみて必要になったもの。

### 9.1 `ON DUPLICATE KEY UPDATE` の代入は左から順に評価され、後の式は更新後の値を見る

リース（§2.8）でこの順に書くと、**期限切れの担当を永久に引き継げない**:

```sql
-- 悪い
expires_at = IF(旧owner = new.owner OR 旧expires_at <= NOW(3), new.expires_at, expires_at),
owner      = IF(旧owner = new.owner OR 旧expires_at <= NOW(3), new.owner, owner)
-- ↑ expires_at を先に伸ばすので、owner の条件 (expires_at <= NOW) がもう成立しない
```

しかも**エラーは出ない**。`internal/lease/lease.go` は、
「fence → owner → expires_at」の順（後の式が前の結果に依存してよい形）にしてある。

### 9.2 送信元の時刻が秒単位だと、同じ秒の中の変化が捨てられる

§2.7 の冪等な書き込みは `既存 < 新着` で比較する。送信元が秒までしか返さないと、
同じ秒に起きた2つ目の変化が「進んでいない」と判定されて**捨てられる**。
その場合は `observed_at` に加えて**連番（シーケンス）**を持たせる必要がある。
`internal/fakesvc` はミリ秒まで返すようにしてある。

### 9.3 「知らない項目を記録する」は、1回だけにしないとログが埋まる

§6.3 の「起動時に1回だけ記録する」は、**実装上も1回に絞る必要がある**。
毎メッセージ検査して毎回ログに出すと、秒あたり数百行が出て、気づくどころではなくなる
（最初の実装で実際にそうなった）。`jsonx.UnknownFieldRecorder` は報告を1回に絞ってある。

### 9.4 メモリの記憶は「最後に観測した値」と「DB に入っていると分かっている値」を分ける

`committed` だけを持つと、画面に出すべき最新値が **DB 書き込みが成功するまで古いまま**になる。
`internal/worker` の `entry` は `latest`（判定・表示用）と `committed`（差分判定用）を別に持つ。
