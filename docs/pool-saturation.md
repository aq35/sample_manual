# EXP-5 接続プールの飽和点

再現:

```bash
eval "$(./scripts/mysql-up.sh --export)"
go test ./internal/poollab/ -run TestEXP5 -v -timeout 20m
```

結果ファイル: [`docs/results/exp-5/20260903-132119-connection-pool-saturation.md`](results/exp-5/20260903-132119-connection-pool-saturation.md)

## 1. 同時実行数を上げるとどうなるか（`MaxOpenConns = 8` 固定・主キー読み）

| 並列 | ops/s | p50 | p99 | 待ち回数 | 待ち合計 |
| --- | --- | --- | --- | --- | --- |
| 1 | 4,316 | 218µs | 454µs | 0 | 0 |
| 2 | 9,657 | 195µs | 428µs | 0 | 0 |
| 4 | 18,118 | 204µs | 507µs | 0 | 0 |
| **8** | **23,921** | 294µs | 997µs | 0 | 0 |
| 16 | 21,472 | 638µs | 2.33ms | 32,228 | 12.0s |
| 32 | 23,829 | 1.03ms | 5.16ms | 35,770 | 36.0s |
| 64 | 23,063 | 2.00ms | 11.8ms | 34,657 | 84.1s |

**飽和点は `MaxOpenConns` と同じ 8。** それを超えると:

- **スループットは伸びない**（23,000 ops/s 前後で頭打ち）
- **遅延だけが線形に伸びる**（p50 は並列2倍ごとに約2倍）
- 超過分は `database/sql` の待ち行列に現れる（`WaitCount` / `WaitDuration`）

> `db.Stats().WaitCount` と `WaitDuration` が 0 でないなら、
> **すでに飽和している**。この2つを監視に出しておくと、飽和点は運用中に分かる。

## 2. `MaxOpenConns` を増やすとどこまで伸びるか（並列 32 固定）

| MaxOpen | ops/s | 前段からの伸び | p99 |
| --- | --- | --- | --- |
| 1 | 4,080 | — | 33.7ms |
| 2 | 8,265 | +102.6% | 16.9ms |
| 4 | 15,371 | +86.0% | 8.73ms |
| 8 | 24,300 | +58.1% | 4.94ms |
| **16** | **27,404** | **+12.8%** | 3.78ms |
| 32 | 27,676 | +1.0% | 4.15ms |

**16 で頭打ち**（この機械は 4 CPU で、MySQL とアプリが同居している）。
これ以上増やしても、伸びるのは接続数だけで仕事は増えない。

> **接続数の上限は「DB が耐えられる数」ではなく「増やしても伸びなくなる数」で決める。**
> 伸びない接続は、待ち行列を DB 側に移すだけで、遅延を悪化させる。

## 3. `MaxIdleConns` の既定値（2）

| MaxIdle | ops/s | 新規接続 | アイドル超過で閉じた接続 |
| --- | --- | --- | --- |
| 2 | 27,289 | 0 | 84 |
| 16 | 27,803 | 0 | 0 |

**負荷が途切れないときは、差はほとんど出ない**（この測定では 1.9%）。
以前 `docs/measurements.md` で「300クエリで新規接続 199 本」という差が出たのは、
**間欠的な負荷**（波がある・アイドル時間がある）だったため。

> `MaxIdleClosed` が増えているなら、接続を捨てて張り直している。
> 定常負荷では軽微だが、**間欠負荷では接続確立のコストがそのまま乗る**（TLS ならなおさら）。

## 4. 遅いトランザクションは接続を占有する

`MaxOpen 4` / 並列 32 / DB 側で 100ms 待つトランザクション:

```
実測 38.7 ops/s（理論上限 = 接続数 ÷ 占有時間 = 4 / 0.1 = 40 ops/s）
待ち 144 回
```

**並列を 32 にしても、上限は動かない。** 上限を決めるのは同時実行数ではなく
**「接続数 ÷ 1件あたりの占有時間」**。

これは `調査` §4.6 の「トランザクションを開いたまま外部 API を呼ばない」と同じ話で、
**占有時間を短くする以外に上限を上げる方法は無い**（接続を増やすと 2 の頭打ちにぶつかる）。

## 5. 適用範囲と未検証

**当てはまる範囲**

- MySQL 8.0 / **同一ホスト**（アプリと MySQL が同じ 4 CPU を分け合う）
- 64 行の表への主キー読みが中心。実データの分布や索引の効き方は含まない
- 1条件あたり 1.5〜3 秒

**保証しないこと**

- **ネットワークを跨ぐ構成**では往復が支配的になり、飽和点は変わる（もっと多くの接続が要る）
- **RDS Proxy などの接続集約**を挟んだ場合 → [`docs/rds-proxy.md`](rds-proxy.md)
- 専用機（DB だけが動く機械）での値とは異なる。ここではアプリと DB が CPU を奪い合っている
- TLS を使っていないので、接続確立のコストは実際より小さい
