# 担当テナント数（IN サイズ）の上限（EXP-16）

- 実験: `internal/fanoutlab` / 結果: [docs/results/exp-16/exp-16-owned-tenant-limit.md](results/exp-16/exp-16-owned-tenant-limit.md)

EXP-14 で fan-out を1クエリ（`WHERE tenant_id IN (owned...)`）に畳んだ。担当テナントが増えると
その1クエリが重くなる。どこからか。

| 担当テナント（IN サイズ） | 1クエリ p95 |
| --- | --- |
| 10 | 0.4ms |
| **30** | **1.0ms** |
| 100 | 2.6ms |
| 300 | 5.0ms |
| 1000 | 16.7ms |

- **テナント 30 なら約 1ms。畳んで良い**（EXP-14 の効果をそのまま受けられる）。
- コストは IN サイズにほぼ比例。
- 畳む vs 分ける（300 テナント）: IN(300) 1クエリ **4.8ms** < IN(100)×3 合計 **6.9ms**。
  300 でもまだ1クエリが有利（分けると往復が増える）。分割が効くのは IN が十分大きく1クエリが重くなってから。

**決め方**: 担当テナント数の上限は、この1クエリ所要と**接続予算（`poolbudget`）**の両方から決める。
30 テナントなら制約にならない。数百を超えるなら、コンテナあたりの担当テナント数に上限を設けて分割。
